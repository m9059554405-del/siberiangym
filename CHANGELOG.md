## [0.41.1] — 2026-09-18

Аудит дифа P2.5–P2.9: три исправления по итогам ревизии, смоук изменённых путей зелёный.

### Исправлено
- **Гонка киоска на одного клиента** (P2.8, `kioskScan`): два терминала, сканирующие один QR одновременно, могли оба пройти проверку «активной аренды нет» и назначить клиенту два шкафчика. Теперь в транзакции назначения сначала блокируется строка клиента (`FOR UPDATE`), аренда перепроверяется под блокировкой — второй скан встаёт в очередь и возвращает тот же шкафчик. Выбор шкафчика по-прежнему `FOR UPDATE SKIP LOCKED` (параллельные назначения разных клиентов не ждут друг друга).
- **doorState на шкафчике без датчика** (P2.8): повторный скан по активной аренде неоснащённого шкафчика больше не пишет `door_state=OPEN` туда, где датчика нет.
- **Форматирование**: восстановлена индентация блока импортов модулей в `app.module.ts` (задета при P2.6).

### Проверено смоуком
- Киоск (точка временно в `centralized_kiosk`): скан → назначен №1; повторный скан → тот же №1 (`repeat=true`, включая новый путь перепроверки в транзакции); `kiosk/release` → дверца открыта, `releasedNow=false`; колбэк `door-state CLOSED` → шкафчик FREE, аренда закрыта. Режим точки и шкафчик возвращены к исходному состоянию, смоук-клиент и записи журнала удалены, сервер остановлен.
- Прочее по ревизии дифа без замечаний: лиды (гейм-скоп, CONVERTED только через конвертацию), no-show/возвраты (запрет на создании и повтор в транзакции), двойное бронирование (preflight + FOR UPDATE в `applyLine`), веб-часть (LeadsPage, CalendarPage, PaymentsPage, OrdersPage), миграции соответствуют схеме.

## [0.41.0] — 2026-09-18

[P2.9] Самостоятельная онлайн-оплата картой в приложении клиента: демо-эквайринг (по плану клуба — Альфа-Банк) с вебхуком банка, заказ закрывается без кассира; фискальный чек по 54-ФЗ выдаёт онлайн-касса платёжного шлюза.

### Добавлено
- **`AcquiringService`** (`api/src/acquiring/`): настройка тремя переменными `ACQUIRING_API_URL / ACQUIRING_API_KEY / ACQUIRING_WEBHOOK_TOKEN`; без них онлайн-оплата скрыта (кнопка не показывается, отправка на оплату — 400). Демо-режим без обращения к банку: синтетический `paymentUrl`, успех приносит тестовый вебхук; реальная интеграция заменяет только тела `createPayment/verifyWebhookToken`, остальной код не меняется.
- **`POST /api/orders/:id/pay/online`** (CLIENT/CEO/STAFF): заказ `DRAFT` → `AWAITING_PAYMENT` + `CARD_ONLINE` + `expiresAt` (просрочка — общий sweep с наличными); в ответе — `paymentUrl` платёжной формы.
- **`POST /api/payments/webhook`** (публичный, авторизация заголовком `x-webhook-token`): `succeeded` → заказ в `PAID` тем же финалом, что и скан чека (позиции применяются, транзакции создаются), сумма сверяется до копейки, повторный вызов идемпотентен (`alreadyPaid`); `failed` → заказ `CANCELLED` с причиной, клиент собирает новый. Строка заказа блокируется `FOR UPDATE` с перепроверкой статуса — вебхук и касса не закроют заказ дважды.
- **`GET /api/payments/online-enabled`** (JWT): показывать ли кнопку «Оплатить картой онлайн»; в PaymentsPage кнопка появляется только при настроенном эквайринге, после создания платежа — редирект на `paymentUrl`.
- **Защита от двойного подтверждения**: скан бумажного чека (`confirm-receipt`) по заказу `CARD_ONLINE` отклоняется 400 — онлайн-заказ закрывается только подтверждением банка.
- Общий финал оплаты вынесен в `commitAsPaid` (общий для чека и вебхука); `OrdersModule` экспортирует `OrdersService` (DI для вебхука).

### Проверено смоуком
- `online-enabled` = true при настроенном эквайринге; клиент создал заказ PACK10 (DRAFT, 8000 ₽) → `pay/online` → AWAITING_PAYMENT/CARD_ONLINE + paymentUrl; `confirm-receipt` по нему — 400; вебхук с неверным/пустым токеном — 403; вебхук с неверной суммой — 400; успех → PAID, абонемент PACK10 10/10 ACTIVE, транзакция 8000 ₽ по заказу; повторный вебхук — alreadyPaid без повторного применения; провал → CANCELLED с причиной, повторный — молча ок; `pay/online` по PAID — 400; `orders/mine` показывает оба заказа с итоговыми статусами.
- Найдено и исправлено смоуком: `OrdersModule` не экспортировал `OrdersService` — рантайм-ошибка DI, которую сборка не ловит; после фикса пересборка и полный прогон зелёные.
- Смоук-данные удалены полностью (клиент, заказы, транзакция, абонемент, логин, activity_log), `ACQUIRING_*` из `.env` убраны, сервер остановлен.

### Известные ограничения (осознанные)
- Демо-провайдер без реального банка: `paymentUrl` синтетический, деньги не списываются, успех симулируется тестовым вебхуком. Реальная интеграция (Альфа-Банк, подпись вебхука) — отдельная задача, контракт кода не меняется.
- Возврат по онлайн-оплаченным заказам — общий механизм P0.7; специфика возврата на карту через банк не реализована.
- Платёжная страница — внешняя (банк); экрана «ожидание оплаты» в приложении нет, статус подтягивается списком заказов и уведомлениями.

## [0.40.0] — 2026-09-17

[P2.8] Централизованное управление шкафчиками: режим точки `centralized_kiosk`, терминал-киоск со сканером QR и драйвер контроллеров замков (демо-заглушка).

### Добавлено
- **Режим точки** (миграция `20260917200000_p2_8_locker_kiosk`): `Gym.lockerMode` — `manual` (по умолчанию, нынешняя аренда через заказ на кассе) | `centralized_kiosk`. Ручной сценарий не меняется; существующие эндпоинты `lockers` целы.
- **Расширение `Locker`**: `bankId` (ряд), `controllerId` + `channelNumber` (сетевой контроллер ряда и релейный выход дверцы), `doorState` (OPEN/CLOSED по датчику, колбэк), `assignedAt`. Поля заполнены только на оснащённых точках; null — обычный шкафчик под ручную аренду.
- **API киоска** (`/lockers/kiosk/*`, CEO/STAFF — терминал авторизован JWT персонала): `scan` — по QR клиента (переиспользован код чек-ина `sgym-checkin:` из P2.2) идемпотентно возвращает закреплённый шкафчик или назначает свободный оснащенный (`FOR UPDATE SKIP LOCKED` — два терминала не назначат один шкафчик, P3.10); `release` — открывает дверцу, аренда закрывается колбэком `door-state` (CLOSED на RENTED → FREE); без датчика — освобождение сразу. Нет свободных → 400; контроллер не ответил → 400 «обратитесь к администратору», шкафчик не занимается. Абонемент НЕ проверяется: доступ к раздевалке ≠ доступ в зал (закрытая развилка бэклога — забрать вещи можно и с истёкшим абонементом).
- **Абстракция железа**: `LockerControllerDriver` (`open(controllerId, channel)`), реальный драйвер подставляется одним `useClass`; в комплекте `LoggingLockerControllerDriver` — логирование без железа (как email/SMS-шлюзы). Колбэк OPEN на свободном шкафчике — warn в лог (сквозной алерт — канал P3.7).
- **Ручная аренда сериализована**: `LOCKER_RENTAL` в подтверждении заказа блокирует строку шкафчика `FOR UPDATE` (закрыт последний check-then-act из P3.10 для заказов).
- **Демо-данные**: 24 шкафчика двумя банками по 12 (контроллеры `kr-a/b-01`, каналы 1–12), два заняты; точка остаётся в `manual`.

### Проверено
- Смоук API на живом сервере: в `manual` скан киоска → 400; после переключения точки — назначение №1, повторный скан того же клиента → тот же №1 (repeat=true), второй клиент → №2, чужой/неверный код → 400; выдача → дверца OPEN, аренда живёт до колбэка, `door-state CLOSED` → шкафчик FREE; повторная выдача корректно переоткрывает дверцу (идемпотентность по смыслу «скан = открыть»); все шкафчики заняты → 400 «нет свободных»; ручная аренда заказом с чеком → PAID, шкафчик RENTED до даты. Пойман и исправлен баг: параметрический роут `:id/release` перехватывал `kiosk/release` (404) — роуты kiosk/* переставлены выше. Драйвер логирует OPEN-команды. База восстановлена пересевом демо, журнал до baseline, сервер остановлен.
- Сборка api чистая (веб не менялся).

### Не покрыто этим пунктом (явно)
- Реальное железо (Kerong/иной контроллер) и терминал: драйвер-заглушка логирует, ПО киоска — за пределами веб-приложения (API-first по бэклогу «реализуется после монтажа оборудования»). UI переключателя режима точки в панели CEO нет — режим меняется через БД/API. Алерт «дверца не закрылась N минут» — только warn-лог, канал алертов появится в P3.7. Киоск-аренда бесплатная на время визита (без заказа/чека) — продуктовое решение; посуточная плата остаётся у ручной аренды. Истинно параллельные сканы двух терминалов не разыгрывались (гарантия SKIP LOCKED; нагрузочные тесты — P3.20).

## [0.39.0] — 2026-09-17

[P2.7] Защита от двойного бронирования: время тренера — неделимый ресурс
сети, время клиента — без пересечений, захват ресурса сериализован в БД.

### Добавлено
- **Время тренера** (`schedule.service.ts`, `assertTrainerFreeAt`): создание персонального слота или группового занятия запрещено, если у тренера уже есть слот/занятие, пересекающееся по времени — по всей сети, без фильтра по точке (тренер работает на нескольких площадках с P1.3). Раньше пересекающиеся активности создавались беспрепятственно, в том числе на разных точках.
- **Время клиента** (`orders.service.ts`, `assertClientFreeAt`): клиент не может оплатить две пересекающиеся по времени активности (персональная × персональная у разных тренеров, персональная × групповая, групповая × групповая). Проверяется при сборке заказа (preflight, 409 с понятным текстом «Двойное бронирование: …») и повторно в транзакции подтверждения чека. Завершённые/пропущенные слоты (PAST_*) остаются занятым временем клиента. Известное окно в секунды при одновременном подтверждении двух заказов одного клиента задокументировано в коде — полная гарантия потребовала бы глобальной блокировки клиента на каждую запись.
- **Сериализация захвата (P3.10 для этих ресурсов)**: подтверждение брони блокирует строку ресурса `FOR UPDATE` до конца транзакции — параллельные подтверждения мест на одно групповое занятие выстраиваются в очередь (вместимость больше не может быть «просажена» гонкой), параллельный захват одного слота двумя клиентами невозможен (раньше оба читали FREE и второй молча затирал бронь первого). Шкафчики остаются check-then-act — P3.10/P2.8.
- Помощник `time-overlap.util.ts`: пересечение интервалов «дата + HH:MM» (занятий через полночь в клубной модели нет).

### Проверено
- Смоук API на живом сервере: слот A оплачен чеком → BOOKED; заказ на пересекающийся слот другого тренера → 409 «двойное бронирование»; заказ на пересекающееся групповое → 409; заказ на непересекающееся групповое → DRAFT → оплата чеком → запись создана; создание слота поверх существующего у тренера → 400; создание группового поверх слота тренера → 400. Проверка тренерского времени сработала и против демо-расписания (первая попытка смоука на занятом слоте была корректно отклонена). Смоук-данные вычищены до baseline (заказы/транзакции/слоты/занятия/уведомления/журнал), сервер остановлен.
- Сборка api чистая (веб не менялся).

### Не покрыто этим пунктом (явно)
- Истинно параллельные подтверждения (два потока одновременно) в смоуке не разыгрывались — гарантия даётся блокировкой Postgres FOR UPDATE, последовательно проверены только сами отказы; нагонять параллелизм — предмет нагрузочного теста P3.20. Захват шкафчиков в заказе не сериализован (P3.10, меняется в P2.8). Окно «два заказа одного клиента подтверждаются одновременно» (разные ресурсы, блокировка каждого по своей строке) — секунды, принято сознательно. Существующие демо-данные инвариантами не ретровалидируются (проверка только на новых записях).

## [0.37.0] — 2026-09-17

[P2.5] Политика no-show/отмены: окно «поздней отмены» и запрет возврата
после оказания услуги (или неявки).

### Добавлено
- **Окно поздней отмены** (`api/src/schedule/schedule.const.ts`): PERSONAL — 12 ч, GROUP — 2 ч; продуктовое решение зафиксировано в коде с обоснованием. Клиент не может сам отменить персональную тренировку ближе 12 ч до начала (400, «свяжитесь с администратором» — форс-мажор решает персонал); CEO/STAFF отменяют без ограничений. Отмена группового занятия не блокируется — место физически освободится и его подберёт лист ожидания (P2.3), но поздняя отмена отмечается в журнале действий («менее 2 ч до начала») для разбора спорных возвратов.

Новый `CreateStaffDto` вообще не принимает `role` — всегда `STAFF`; CLIENT/TRAINER по-прежнему заводятся только через свои профильные модули, где сразу создаётся и бизнес-карточка.
- **[P1.10] `User.name`** (миграция `20260917002507_p1_10_user_name`) — раньше сотрудник с ролью STAFF в журнале изменений был неотличим от любого другого STAFF: `resolveActorName` возвращал жёстко строку `«Администратор»` на всех. Теперь ФИО указывается при заведении и видно в каждой записи журнала как имя конкретного человека.
- **[P1.10] Явное решение по смене роли, а не оставлено неявным, как просил документ.** Роль после создания учётной записи неизменяема в этой версии — нет `PATCH /users/:id/role`. Причина: аудируемая смена роли осмысленна только вместе с деактивацией старой роли (иначе можно тихо получить доступ на несколько ролей сразу), а сама деактивация (P3.9) ещё не реализована — добавлять один без другого means либо непроверенный код, либо функциональность с дырой. Единственный сегодняшний путь сменить роль сотруднику — завести новую учётную запись, старую не отзывать (тоже ждёт P3.9).

### Исправлено (найдено при подготовке этого пункта — регрессия из P1.1, не из более ранней версии)
- **Бутстрап на пустой БД был сломан для только что выпущенного P1.1.** `Gym.networkId` стал обязательным полем в 0.21.0, а `prisma/seed.ts` по-прежнему создавал `Gym` без него — первое разворачивание системы (`prisma migrate deploy && prisma db seed`, ровно то, что описывает `DEPLOY_GUIDE.md`) упало бы сразу на первом же шаге. Причина глубже опечатки: `Gym` требует существующую `Network`, `Network` в обычном варианте требовала бы существующего владельца-CEO (`User`), а `User` требует существующий `Gym` — настоящая циклическая зависимость трёх сущностей при самом первом бутстрапе, а не что-то, что можно было решить только порядком операций.
- **Починка:** `Network.ownerId` перестал быть внешним ключом на уровне БД (обычным полем с уникальным индексом остался) — это единственная точка цикла, где реальной необходимости в FK нет: удаления `User` в системе не существует вообще (P3.9 — деактивация, не удаление), а все сетевые эндпоинты (`resolveOwnedNetworkId`) и так явно проверяют владельца при каждом обращении, не полагаясь на ограничение БД. Это разрывает цикл: `seed.ts` теперь создаёт `Network` (с заранее сгенерированным `id` будущего CEO в качестве `ownerId`) → `Gym` (ссылается на готовую `Network`) → `User` (с тем самым заранее сгенерированным `id`, ссылается на готовый `Gym`) — три обычных, непротиворечивых вставки по порядку, без вставки в базу «сначала, чинить потом».
- Проверено прогоном на пустой БД: `prisma migrate deploy` (все 11 миграций, включая эту) и `prisma db seed` на только что созданной, ранее нетронутой БД — оба шага завершились без ошибок, `Network`/`Gym`/`User` (CEO) созданы с корректными перекрёстными ссылками; повторный запуск `seed` корректно идемпотентен (не создаёт дублей).
