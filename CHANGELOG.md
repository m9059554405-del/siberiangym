# Changelog

Все значимые изменения проекта фиксируются в этом файле.
Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/).

## [0.11.0] — 2026-09-11

PWA-обвязка — приложение можно установить на экран телефона как
"настоящее" приложение, без публикации в App Store/Google Play (решение
зафиксировано ещё в 0.1.0 из-за сроков).

### Добавлено
- **`vite-plugin-pwa`**: манифест (`SiberianGym`, тема в фирменном синем `#0369a1`, `display: standalone`), service worker с офлайн-кэшем статики (запросы к `/api/*` — только сеть, реальные данные никогда не кэшируются как статика).
- **Иконки приложения**: сгенерированы напрямую (192/512/512-maskable/apple-touch-icon) — фирменный градиент с иконкой штанги, без внешних ассетов.
- `index.html`: `apple-touch-icon`, `theme-color`, `lang="ru"`, описание — для корректного вида при добавлении на экран телефона на iOS и Android.
- Убраны неиспользуемые файлы из шаблона Vite (`favicon.svg`, `icons.svg` от демо-страницы заглушки, которых в проекте больше нет).

### Проверено
- Продакшн-сборка (`vite build` + `vite preview`): манифест и иконки отдаются корректно, `sw.js` генерируется и валиден. Саму регистрацию service worker в этой сессии проверить не удалось — песочница превью-браузера блокирует `navigator.serviceWorker.register()` (сам файл при этом отдаётся нормально) — это ограничение окружения предпросмотра, а не приложения; конфигурация стандартная и должна нормально работать в реальном браузере на телефоне.

## [0.10.0] — 2026-09-11

Кабинет CEO — последняя из четырёх ролей. Все разделы демо перенесены
на реальные данные: загрузка тренеров, посещаемость, выручка,
клиентская база, склад, обслуживание клуба, рассылки, журнал
изменений. **С этой версии весь функционал демо перенесён на реальный
backend для всех четырёх ролей** (Клиент, Тренер, Администратор, CEO).

### Добавлено
- **`GET /transactions`** (CEO): все финансовые транзакции зала — раньше данные о продажах нигде не были доступны за пределами самого создания записи, выручку посчитать было не из чего.
- **`GET /workout-logs`** (CEO/STAFF): все тренировки по залу (не по одному клиенту) — нужно для графика посещаемости.
- **`web/src/features/ceo/`**: загрузка тренеров (график + карточка добавления тренера с выдачей доступа), посещаемость (динамика по дням/неделям, время посещений, занятость тренеров по часам), выручка (по дням/месяцам/источникам, топ тренеров), клиентская база (формат/статус абонементов, смены тренера), карточка тренера (подопечные, платежи), обслуживание (оборудование + клининг + обращения к директору в одном месте), рассылки (CRUD предложений по аудитории), журнал изменений (полная история действий всех ролей).
- Добавление тренера доступно прямо из «Загрузки тренеров» — раньше тренеров можно было завести только напрямую через API.

### Исправлено
- **`GET /clients`** не отдавал историю смены тренера/формата (`formatHistory`) — из-за этого раздел «Клиентская база» не мог показать, кто менял тренера.

### Сознательно не перенесено (зафиксировано на будущее)
- **Экспорт отчётов в PDF** (`utils/clientReport.ts` в демо, ~570 строк генерации PDF по клиенту/тренеру/всем активным) — большой самостоятельный кусок функциональности, не критичный для запуска. Экран и данные, из которых отчёт строился бы, уже на месте (карточка тренера, клиентская база) — добавить экспорт можно отдельной задачей.

### Проверено
- Полный сквозной сценарий CEO: создан тренер с выдачей доступа → клиент выбрал этого тренера с тарифом «Ведение» и продлил абонемент → выручка (9 400 ₽) корректно разбита по категориям → карточка тренера показывает того же клиента и тот же платёж → клиентская база и журнал изменений (29 записей) отражают все действия → рассылка создана и сохранена.
- Очистка: после каждой проверки тестовые данные (клиенты, тренеры, транзакции, журнал) удалены из базы.

## [0.8.0] — 2026-09-11

Кабинет тренера — список подопечных, карточка клиента (программа,
история тренировок, прогресс по мышцам, замеры, фото, обратная связь)
и личное расписание. Плюс важная инфраструктурная вещь: раньше у CEO
физически не было способа выдать клиенту или тренеру доступ в
приложение — только я мог это сделать вручную через базу при
тестировании. Теперь это нормальный эндпоинт.

### Добавлено
- **`POST /clients/:id/create-login`, `POST /trainers/:id/create-login`** (CEO/STAFF): выдаёт клиенту/тренеру доступ в приложение — создаёт учётную запись и привязывает её к уже существующей карточке. До этого карточку можно было завести, а войти в приложение под ней было физически нечем.
- **`GET /trainers/me`, `GET /trainers/me/clients`**: тренер видит свой профиль и список своих подопечных.
- **`GET /clients/:id`** теперь доступен тренеру — но только на своих подопечных (проверка владения), не на любого клиента зала.
- **`web/src/features/trainer/`**: список подопечных с фильтром по формату, карточка клиента (редактирование программы, график прогресса рабочего веса по ключевому упражнению, история тренировок, диаграмма нагрузки по мышцам, замеры, фото от клиента, переписка), расписание тренера (список по неделям + календарь).

### Проверено
- Вход тренером → список из одного назначенного подопечного → открыл карточку → добавил день в программу (сохранилось, `assignedBy: trainer`) → расписание отображается корректно (пусто, слотов ещё нет).

### Проверено
- Клиент без тренера: добавил день тренировки → добавил упражнение из библиотеки → провёл тренировку через `WorkoutLogger` → статус «Выполнено» рассчитан на backend автоматически по факту выполненных подходов → отражён в истории.

## [0.5.0] — 2026-09-11

Старт фронтенда (`web/`, Vite + React 19 + TypeScript). Реальный вход по
JWT, ролевой роутинг на все четыре роли, и полностью рабочий раздел
клиента (оплата, тренер, календарь, магазин) — проверено в браузере на
реальных данных через настоящий backend, а не моки.

### Добавлено
- **Каркас фронтенда** (`web/`): Vite + React 19 + TypeScript, Tailwind CSS v4 (визуальный стиль перенесён из демо без изменений, как и просил заказчик), React Router v7 (`HashRouter` — как в демо, чтобы не требовать серверных правил переадресации на дешёвом хостинге), TanStack Query v5 для серверного состояния (вместо localStorage-как-базы из демо), Zustand — только для локального состояния авторизации.
- **Экран входа** (`web/src/pages/LoginPage.tsx`): вход по email/паролю, сохранение JWT и роли, редирект в кабинет нужной роли.
- **Ролевой роутинг**: `/client`, `/trainer`, `/staff`, `/ceo` — каждый защищён своей ролью (`RequireRole`), попытка зайти не в свой раздел редиректит в свой кабинет. Разделы Тренера/Администратора/CEO пока заглушки — появятся в следующих версиях; сейчас полностью готов раздел Клиента.
- **Раздел клиента** — перенесён из демо на реальный API через React Query:
  - **Оплата**: текущий абонемент, покупка/продление, тариф сопровождения, обратная связь директору.
  - **Тренер**: список тренеров, выбор/смена тренера и тарифа, переход на самостоятельные тренировки.
  - **Календарь**: групповые занятия (запись/отмена) и персональные слоты (для тарифа «Индивидуальные тренировки»), список и календарная сетка.
  - **Магазин**: аренда/освобождение шкафчика, покупка воды и еды из справочника.

### Добавлено (backend, по ходу подключения фронтенда)
- `GET /clients/me` — собственная карточка клиента (резолвится по токену, не по параметру).
- `GET /workout-logs/mine`, `GET /measurements/mine`, `GET /progress-photos/mine` — раньше эти данные мог читать только тренер/CEO/STAFF, сам клиент свои же тренировки/замеры/фото прочитать не мог.
- `GET /pricing` — цены абонементов и услуг зала (раньше нигде не отдавались наружу, хотя использовались в покупке).
- `POST /stock/purchase` + `GET /stock/catalog` открыт клиенту — покупка воды/еды в приложении (как в демо: фиксирует транзакцию, без учёта остатков).
- `trainers.findAll` теперь возвращает часы работы/сертификаты/фото тренера (нужно для карточки тренера в приложении клиента), раньше это отдавалось только в чтении одного тренера.

### Исправлено
- **Дыра в авторизации**: `GET /clients/:clientId/program` и `GET /clients/:clientId/feedback` не проверяли, что клиент запрашивает СВОЮ карточку — авторизованный клиент мог подставить чужой id и прочитать чужую программу тренировок или чужую переписку с тренером. Добавлена проверка владения, как уже было сделано в остальных self-service методах.
- **`RootLayout` не пускал на экран входа**: компонент возвращал `null` целиком, если пользователь не авторизован, из-за чего дочерний редирект на `/login` никогда не успевал сработать — приложение показывало пустую страницу вместо формы входа. Исправлено: неавторизованный пользователь всегда получает `<Outlet />`.

### Проверено
- Полный сквозной сценарий в браузере на реальном backend (без моков): вход клиентом → покупка абонемента → выбор тренера и тарифа → запись на групповое занятие → аренда шкафчика → покупка воды — каждое действие подтверждено в интерфейсе и очищено из базы после проверки.
- Вход CEO → ролевой редирект в `/ceo`, попытка клиента зайти в чужой раздел корректно отбрасывает в свой.

### Дальше по плану
- Разделы «Упражнения», «Прогресс», «Новости» клиента (сейчас заглушки).
- Кабинеты Тренера, Администратора и CEO.
- PWA-обвязка, деплой.

## [0.4.0] — 2026-09-11

Backend теперь покрывает весь функционал демо-версии на уровне API —
все 21 бизнес-модуль перенесены и проверены.

### Добавлено
- **Упражнения** (`api/src/exercises/`): справочник, доступен всем ролям, создают тренер/CEO/STAFF.
- **Программы тренировок** (`api/src/programs/`): у клиента ровно одна актуальная программа (`Program.clientId` теперь уникальный), задаётся тренером/CEO/STAFF или самим клиентом — при обновлении дни и упражнения полностью пересоздаются.
- **Логи тренировок** (`api/src/workout-logs/`): клиент логирует выполнение самостоятельно, статус (выполнено/частично/пропущено) считается автоматически по факту выполненных подходов.
- **Шкафчики** (`api/src/lockers/`): аренда (с транзакцией по цене за день) и освобождение.
- **Новости клуба** (`api/src/club-posts/`): публикация администрацией, видна всем ролям.
- **Обратная связь клиент↔тренер** (`api/src/feedback/`): переписка по карточке клиента.
- **Здоровье клиента** (`api/src/health/`): фото прогресса, замеры (включая биоимпедансометрию), женский календарь — всё строго self-service, привязано к собственной карточке клиента через токен.

### Проверено
- Полный self-service сценарий от лица реального клиентского логина (не администратора): чтение своей программы, логирование тренировки, добавление замера, отметка в женском календаре, сообщение тренеру, аренда шкафчика — всё корректно резолвится по `userId` из токена, а не по параметру из запроса (нельзя подменить чужого клиента).
- Журнал изменений корректно НЕ фиксирует рутинные самостоятельные действия клиента (бронирования, логи тренировок) — так же, как было осознанно решено в демо-версии, чтобы не размывать журнал шумом.

## [0.3.0] — 2026-09-11

Перенесены все оставшиеся разделы демо-версии на реальный backend: расписание,
склад, оборудование/ППР, клининг, обращения к директору, рассылки, обзвон
клиентов. Модель данных из 0.1.0 полностью ожила.

### Добавлено
- **Расписание** (`api/src/schedule/`): групповые занятия (создание, запись клиента, отмена) и персональные слоты (создание тренером, запись, отмена, отметка явки/неявки). Запись создаёт транзакцию по цене зала/тренера, как в демо.
- **Склад** (`api/src/stock/`): справочник товаров, приход, списание (с обязательной причиной — истёк срок/повреждено/продано без чека/использовано клубом/утеряно/другое), инвентаризация с автоматической корректировкой остатков (излишек — новой партией, недостача — списанием со старейших по сроку годности партий), история операций. И CEO, и STAFF управляют складом наравне.
- **Оборудование и ППР** (`api/src/equipment/`): создание карточки оборудования, отметка планового обслуживания выполненным с автоматическим расчётом следующего срока по интервалу.
- **Клининг** (`api/src/cleaning/`): чек-лист на 7 зон создаётся автоматически при создании дня уборки, отметка/снятие отметки по каждому пункту.
- **Обращения к директору** (`api/src/director-messages/`): клиент пишет, CEO отвечает, отметка "прочитано" по ответу.
- **Предложения для рассылки** (`api/src/report-offers/`): создание, включение/выключение, удаление — доступно только CEO.
- **Обзвон клиентов** (`api/src/outreach/`): список клиентов с последней заметкой по звонку; записывать результат звонка может только STAFF (Администратор), CEO видит в режиме просмотра — как и в демо-версии.

### Исправлено
- **Утечка хеша пароля**: `POST /auth/users` возвращал весь объект пользователя, включая `passwordHash` (в захешированном виде, но всё равно не должен покидать сервер). Теперь ответ явно ограничен нужными полями.

### Проверено
- Полный сквозной сценарий по всем новым разделам одним скриптом: тренер → клиент → товар → приход (+50) → списание (−5, причина «повреждено») → остаток 45 подтверждён → инвентаризация (пересчитали на 40) → автоматическая недостача −5 подтверждена → оборудование с ТО и пересчётом следующей даты → чек-лист уборки на 7 пунктов → групповое занятие с записью клиента → персональный слот с записью и отметкой явки → предложение для рассылки → обзвон клиента (под правильной ролью STAFF, доступ CEO корректно отклонён 403).

## [0.1.0] — 2026-09-11

Старт рабочей (не демо) версии SiberianGym. Заложен фундамент: модель данных,
авторизация, первый защищённый модуль — проверено реальными запросами
end-to-end (вход → токен → создание клиента → чтение из базы).

### Решения по проекту (зафиксировано на будущее)
- **Оплата абонементов пока вручную** (администратор отмечает "оплачено"), без реальной интеграции с банком — сделано намеренно, чтобы не ждать оформления ИП/юрлица. Архитектура платежей построена так, чтобы позже подключить настоящий эквайринг (скорее всего Альфа-Банк), не переделывая остальное: как только будет ИП — добавляем реальную оплату картой на этом же месте.
- **Мультиарендность заложена с первого дня**: у каждой таблицы в базе есть привязка к залу (`gymId`). Сейчас в системе один зал — SiberianGym, но добавить второй зал для продажи системы другим клубам — это создать новую запись, а не переделывать структуру.
- **"Мобильная версия" реализуется как PWA** (сайт, устанавливаемый на экран телефона как приложение), а не отдельные приложения под iOS/Android — из-за сроков (4 недели) и того, что публикация в App Store/Google Play требует отдельного длительного процесса модерации и платных аккаунтов разработчика. Отдельная задача на будущее, если понадобятся "настоящие" приложения из сторов.
- **Уведомления на старте — только email** (без SMS, дороже и не обязательно для первого запуска).

### Добавлено
- **Backend** (`api/`, NestJS + TypeScript): каркас приложения, конфигурация через `.env`.
- **База данных** (`api/prisma/schema.prisma`, PostgreSQL + Prisma): полная модель данных перенесена из демо-версии — клиенты, тренеры, абонементы, тренировки, программы, групповые занятия, персональные слоты, шкафчики, склад (партии/списания/приходы/инвентаризация), оборудование и ППР, клининг, обращения к директору, предложения для рассылки, журнал изменений, обзвон клиентов. Плюс новое: `Gym` (зал/арендатор), `User` (учётная запись для входа), `MembershipPricing` (цены теперь настраиваются на уровне зала, а не зашиты в коде).
- **Авторизация** (`api/src/auth/`): вход по email/паролю (JWT), хеширование паролей (bcrypt), защита эндпоинтов по ролям (CEO/STAFF/TRAINER/CLIENT) через guard'ы, привязка каждого запроса к своему залу.
- **Модуль клиентов** (`api/src/clients/`): создание клиента с автоматическим расчётом даты окончания абонемента (перенесено из логики демо-версии), список, просмотр, редактирование — с проверкой ролей и изоляцией по залу.
- **Seed-скрипт** (`api/prisma/seed.ts`): создаёт зал SiberianGym и первую учётную запись CEO при первом развёртывании.
- **Docker Compose** для локальной PostgreSQL при разработке.
