# Changelog

Все значимые изменения проекта фиксируются в этом файле.
Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/).

## [0.2.0] — 2026-09-11

### Добавлено
- **Журнал изменений** (`api/src/activity-log/`) — единая точка записи "кто/что/когда/на что повлияло" для всех значимых действий в системе, доступна CEO через `GET /api/activity-log`. Переиспользуется всеми остальными модулями.
- **Модуль тренеров** (`api/src/trainers/`): список (видят все роли), просмотр карточки, создание тренера (CEO/STAFF).
- **Ключевые действия с клиентом** — перенесены из демо-версии на реальный API:
  - `POST /clients/:id/choose-trainer` — выбор тренера и тарифа, с историей смены формата и транзакцией.
  - `POST /clients/:id/change-tariff` — смена тарифа.
  - `POST /clients/:id/go-self-training` — переход на самостоятельные тренировки.
  - `POST /clients/:id/purchase-membership` — оформление/продление абонемента по ценам зала.
  - Эти действия доступны и CEO/STAFF (управление любым клиентом), и самому клиенту (только своей карточкой) — проверка встроена в сервис.

### Проверено
- Полный сценарий на реальных запросах: создание тренера → создание клиента → выбор тренера с тарифом «Ведение» (формат автоматически стал «Группа», история форматов корректно закрылась и открылась заново) → продление абонемента → журнал изменений содержит все 4 действия в правильном порядке с точными деталями.

## [0.1.0] — 2026-09-11

Старт рабочей (не демо) версии SiberianGym. Заложен фундамент: модель данных,
авторизация, первый защищённый модуль — проверено реальными запросами
end-to-end (вход → токен → создание клиента → чтение из базы).

### Решения по проекту (зафиксировано на будущее)
- **Оплата абонементов пока вручную** (администратор отмечает "оплачено"), без реальной интеграции с банком — сделано намеренно, чтобы не ждать оформления ИП/юрлица. Архитектура платежей построена так, чтобы позже подключить настоящий эквайринг (скорее всего Альфа-Банк), не переделывая остальное: как только будет ИП — добавляем реальную оплату картой на этом же месте.
- **Мультиарендность заложена с первого дня**: у каждой таблицы в базе есть привязка к залу (`gymId`). Сейчас в системе один зал — SiberianGym, но добавить второй зал для продажи системы другим клубам — это создать новую запись, а не переделывать структуру.
- **"Мобильная версия" реализуется как PWA** (сайт, устанавливаемый на экран телефона как приложение), а не отдельные приложения под iOS/Android — из-за сроков (4 недели) и того, что публикация в App Store/Google Play требует отдельного длительного процесса модерации и платных аккаунтов разработчика. Отдельная задача на будущее, если понадобятся "настоящие" приложения из сторов.
- **Уведомления на старте — только email** (без SMS, дороже и не обязательно для первого запуска).

### Добавлено
- **Backend** (`api/`, NestJS + TypeScript): каркас приложения, конфигурация через `.env`.
- **База данных** (`api/prisma/schema.prisma`, PostgreSQL + Prisma): полная модель данных перенесена из демо-версии — клиенты, тренеры, абонементы, тренировки, программы, групповые занятия, персональные слоты, шкафчики, склад (партии/списания/приходы/инвентаризация), оборудование и ППР, клининг, обращения к директору, предложения для рассылки, журнал изменений, обзвон клиентов. Плюс новое: `Gym` (зал/арендатор), `User` (учётная запись для входа), `MembershipPricing` (цены теперь настраиваются на уровне зала, а не зашиты в коде).
- **Авторизация** (`api/src/auth/`): вход по email/паролю (JWT), хеширование паролей (bcrypt), защита эндпоинтов по ролям (CEO/STAFF/TRAINER/CLIENT) через guard'ы, привязка каждого запроса к своему залу.
- **Модуль клиентов** (`api/src/clients/`): создание клиента с автоматическим расчётом даты окончания абонемента (перенесено из логики демо-версии), список, просмотр, редактирование — с проверкой ролей и изоляцией по залу.
- **Seed-скрипт** (`api/prisma/seed.ts`): создаёт зал SiberianGym и первую учётную запись CEO при первом развёртывании.
- **Docker Compose** для локальной PostgreSQL при разработке.

### Проверено
- Полная цепочка на реальных HTTP-запросах: вход → JWT-токен → создание клиента (с кириллицей — проверено, что база хранит корректно) → чтение списка клиентов. Доступ без токена и с неверным паролем корректно отклоняется (401).
- `npx nest build` — сборка backend без ошибок.
- Миграция применяется к чистой базе без ошибок, создаёт 42 таблицы.
