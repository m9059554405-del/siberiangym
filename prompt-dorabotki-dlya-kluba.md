# Промт для Claude Code: доработки SiberianGym для запуска в реальном клубе

> Готово к вставке в Claude Code как есть. Ниже — контекст проекта и приоритизированный список задач, основанный на критическом разборе `CHANGELOG.md` (версии 0.1.0–0.14.0) глазами сеньор-разработчика и управляющего фитнес-клубом. Нумерация вида `P0.1`, `P1.3` — это приоритет и порядковый номер внутри него, используй её при ссылках между пунктами и в коммитах/PR.

---

## Контекст для Claude Code

Ты работаешь над **SiberianGym** — production-системой управления фитнес-клубом:
- Backend: NestJS + TypeScript, PostgreSQL + Prisma, JWT-авторизация, 4 роли (CLIENT, TRAINER, STAFF, CEO), мультиарендность через `gymId`.
- Frontend: Vite + React 19 + TypeScript, Tailwind v4, React Router v7 (HashRouter), TanStack Query v5, PWA (vite-plugin-pwa).
- Деплой: Docker Compose (Postgres + API + nginx), VPS в РФ (Timeweb/Selectel), пока без HTTPS-домена.
- **Целевая конфигурация сервера: 6 vCPU / 12 ГБ RAM / 120 ГБ NVMe + отдельное S3-совместимое хранилище на 500 ГБ.** Это больше, чем минимум «2 vCPU / 4 ГБ RAM / 40–60 ГБ SSD» из `DEPLOY_GUIDE.md` — тот минимум фигурирует в нескольких пунктах ниже как база для расчётов (пул соединений, число инстансов PM2, риск OOM), пересчитано под целевую конфигурацию, где это меняет вывод. `DEPLOY_GUIDE.md` стоит обновить отдельно, чтобы там фигурировала эта целевая конфигурация, а не только «минимум» — иначе следующий, кто будет разворачивать прод по гайду, недооценит реально закладываемые ресурсы. Наличие отдельного S3 на 500 ГБ также подтверждает решение по P0.5 — это внешнее объектное хранилище, а не MinIO на том же VPS.
- Функционал по ролям уже реализован end-to-end на реальном API (не моки): абонементы, тренеры, программы тренировок, логи тренировок, расписание (групповые/персональные), склад, оборудование/ППР, клининг, обращения к директору, рассылки, обзвон, журнал изменений, email-уведомления (через console.log пока нет SMTP).

Все версии до 0.14.0 включительно закрывают функциональный паритет с демо-версией. Ниже — то, чего в демо не было и что нужно **дополнительно**, чтобы систему можно было безопасно и легально эксплуатировать в реальном клубе, а не только в качестве MVP для одного зала владельца.

Работай по пунктам ниже как по бэклогу: для каждого — отдельная ветка/коммит, с миграциями Prisma где нужно, и с обязательной секцией "Проверено" в `CHANGELOG.md` в том же стиле, что уже используется в проекте (ручной сквозной сценарий + очистка тестовых данных).

## Приоритет 0 — блокирует легальный запуск (сделать до приёма первого реального платежа)

**P0.1. Работающая сертифицированная онлайн-касса на каждый платёж (54-ФЗ).** Здесь важно разделить два разных требования, которые легко перепутать:
- **Юридический минимум — просто наличие кассы.** Приём денег от физлиц без выдачи фискального чека — нарушение 54-ФЗ, независимо от того, кто и как этот чек пробивает. Этому требованию полностью удовлетворяет обычный отдельно стоящий кассовый аппарат/терминал (АТОЛ, Эвотор и т.п.), купленный и зарегистрированный в ФНС через ОФД — это закупка и регистрация, организационный шаг клуба, а не задача для Claude Code. Администратор пробивает чек на этом аппарате вручную, программе не обязательно быть с ним как-либо интегрированной.
- **Что тогда реально нужно от софта — не дать системе разойтись с реальностью.** Раньше (0.1.0–0.14.0) оплата — это администратор просто отмечает «оплачено» в интерфейсе, без какого-либо подтверждения того, что чек вообще был пробит. Вот это и есть настоящий блокер: не отсутствие кассы (её можно купить за день), а отсутствие в софте механизма подтверждения, что деньги реально прошли через кассу. Этот механизм — P0.2 ниже (приём чека сканированием). Минимум для легального и честного по деньгам запуска — это связка «любая сертифицированная касса» + P0.2, и её можно собрать без единой строчки интеграции с ОФД.
- **Более глубокая интеграция — не блокер, а автоматизация на потом.** Если вместо этого бэкенд сам программно генерирует чек через API ОФД/эквайринг-провайдера (АТОЛ Онлайн, CloudKassir, или эквайринг вроде Т-Бизнес/Альфа-Банка, который сам пробивает чек) — это убирает у администратора ручной шаг «пробить на отдельном аппарате», снимает риск разойтись суммами и упрощает эксплуатацию при росте потока. Это полезно и стоит сделать, но это уже не условие легального старта, если P0.2 реализован — переносить в Приоритет 3 как автоматизацию, если не хочется делать сразу.

**P0.2. Приём кассового чека в систему сканированием QR/штрихкода — подтверждение заказа.** Это конкретный механизм, который делает P0.1 реальным на уровне софта, а не только на бумаге: деньги физически принимает администратор через кассовый терминал (свой отдельный аппарат или, позже, через интеграцию из P0.1), и система должна не просто верить ему на слово, а требовать подтверждение реальным чеком, прежде чем считать заказ оплаченным.

Модель процесса:

- **Заказ (`Order`) вместо прямого создания транзакции.** Сейчас `purchase-membership`, `change-tariff`, `POST /stock/purchase`, аренда шкафчика и т.д. каждое сразу создают `Transaction`. Нужно ввести промежуточную сущность `Order` (`id`, `clientId`, `gymId`, `createdBy`, `status`: `draft` → `awaiting_payment` → `paid`/`cancelled`, `paymentMethod`: `cash`/`card_online`, `totalAmount`, `receiptData`) и дочернюю `OrderLine` (`type`: `membership_purchase`/`membership_renewal`/`tariff_change`/`stock_purchase`/`locker_rental`/…, `refId`, `amount`). Администратор собирает заказ из одной или нескольких строк (см. пример ниже), система считает `totalAmount` как сумму строк.
- **Групповой чек.** Пример из задачи: продление абонемента + покупка воды в одном чеке. Это один `Order` с двумя `OrderLine` (`membership_renewal` на стоимость абонемента, `stock_purchase` на воду), `totalAmount` — их сумма. Администратор пробивает на кассе один чек на всю сумму сразу, сканирует один раз — закрывает весь заказ целиком, а не по отдельным позициям.
- **Сценарий администратора (наличные):** собрал заказ → нажал «Провести оплату наличными» → `Order` переходит в `awaiting_payment` → пробивает реальный чек на кассе на сумму `Order.totalAmount` → сканирует QR или штрихкод с распечатанного чека. Явно реши и зафиксируй одну стратегию применения изменений: либо ничего не применяется (абонемент не продлевается, склад не списывается), пока чек не подтверждён — это безопаснее для денег и рекомендуется по умолчанию; либо применяется сразу с откатом при непройденном подтверждении — тогда нужно явно продумать откат для каждого из шести сценариев ниже. Не оставляй это на усмотрение реализации по ходу дела.
- **Разбор чека.** Фискальный QR российской онлайн-кассы — стандартный формат ФНС: `t=<дата-время>&s=<сумма>&fn=<номер ФН>&i=<номер документа>&fp=<фискальный признак>&n=<тип операции>`. Сверяется `s` (сумма чека) с `Order.totalAmount` с точностью до копейки. Совпало — `Order` переходит в `paid`, применяются все отложенные действия по всем `OrderLine`, создаётся `Transaction`, `receiptData` (включая сырую строку QR) сохраняется в `Order` для аудита. Не совпало — заказ не закрывается, администратору явно показывается расхождение (в чеке X ₽, в заказе Y ₽), заказ остаётся открытым до повторного сканирования корректного чека или отмены.
- **Один чек — один заказ.** Уникальный ключ чека `fn + i + fp` должен быть уникальным индексом в базе. Повторное сканирование уже использованного чека для другого заказа — жёсткая ошибка, попытка отдельно фиксируется в `activity-log` как подозрительная (единственная защита от подстановки одного и того же чека под несколько заказов).
- **Сканер.** Поддержать оба варианта, которые реально есть на ресепшене: обычный USB/Bluetooth-сканер штрихкодов, работающий как клавиатура (просто фокус на поле ввода и быстрый ввод строки с Enter в конце — никакого специального драйвера не нужно), и камеру телефона/планшета через уже существующий PWA (библиотека чтения QR в браузере, например `@zxing/browser` или `html5-qrcode`) — для администраторов без выделенного сканера.
- **Выбор способа оплаты в приложении клиента.** При нажатии кнопки оплаты (продление, покупка воды и т.д.) — выбор: «Оплатить наличными администратору», и опционально «Оплатить картой онлайн», если реализован P2.9 (самостоятельная безналичная оплата без участия администратора). «Наличными» создаёт `Order` в `awaiting_payment` и переводит клиента в сценарий администратора выше (подтверждение сканированием на ресепшене) — этого достаточно для легального запуска самого по себе, второй вариант оплаты не обязателен для старта. Если P2.9 не реализован — кнопка «Картой онлайн» в интерфейсе просто не показывается, это не блокирует запуск. Когда P2.9 появится — после подтверждения оплаты банком `Order` сразу переходит в `paid` без сканирования (чек в этом случае обязателен по 54-ФЗ так же, как и при наличных, но выдаётся автоматически платёжным шлюзом/онлайн-кассой).

- **Ценовой снэпшот.** `OrderLine.amount` — это сумма по цене на момент СОЗДАНИЯ заказа, а не значение, пересчитываемое на лету при оплате. Конкретный сценарий бага: CEO меняет цену тарифа или товара (P4.2) в промежутке между тем, как клиент/администратор создал заказ, и тем, как чек был пробит и отсканирован — если сумма при подтверждении пересчитывается заново по актуальной цене, чек (пробитый по старой цене) разойдётся с пересчитанным `Order.totalAmount`, и легитимный платёж будет ошибочно отклонён как «несовпадение сумм».
- **Просроченные («брошенные») заказы.** `Order` в `awaiting_payment`, который никто не подтвердил (клиент передумал, администратора отвлекли, кончилась смена) должен автоматически переходить в `expired`/`cancelled` по настраиваемому таймауту (например, 2 часа) — иначе такие заказы копятся бессрочно и путают администратора при следующей попытке оформить тому же клиенту новый заказ («это тот старый или новый?»).
- **Заказ не привязан намертво к создавшему его администратору.** Если заказ создал администратор утренней смены, а клиент донёс чек вечером — другой администратор на той же точке должен видеть и мочь закрыть этот же `Order`. Значит, видимость и права на завершение `Order` — по точке (`gymId`), а не только по `createdBy`.

**Обязательная сверка зависимостей перед реализацией P0.2.** Этот пункт оборачивает все существующие денежные действия в проекте — нельзя добавлять `Order`/`OrderLine` рядом со старой логикой, оставляя два параллельных пути создания транзакций. Перед началом работы явно пройтись и перечислить в описании PR все места, которые сейчас напрямую создают `Transaction` или списывают склад:
1. `POST /clients/:id/purchase-membership`
2. `POST /clients/:id/change-tariff`
3. `POST /clients/:id/go-self-training` (если тарифицируется)
4. `POST /stock/purchase` (покупка клиентом воды/еды, 0.5.0)
5. Аренда шкафчика (`lockers`, 0.4.0)
6. Запись на групповое/персональное занятие — «запись создаёт транзакцию по цене зала/тренера» (0.3.0)

Для каждого из них проверить: (а) тип операции покрывается существующим enum'ом в `prisma/schema.prisma` (посмотреть, что там уже есть, и не заводить рядом второй похожий enum с другим набором значений под ту же суть); (б) массивы/списки на фронтенде, которые группируют выручку по источникам в CEO-отчётности (0.10.0, «выручка... по источникам, топ тренеров») — обновлены под новый источник `OrderLine.type`, а не задублированы отдельной логикой группировки; (в) TypeScript-типы/DTO на фронте (`web/src/features/...`), описывающие транзакцию/оплату, синхронизированы с новыми полями `Order`/`paymentMethod`; (г) запись в `activity-log` идёт через уже существующий общий механизм логирования (переиспользуется всеми модулями с 0.2.0), а не отдельным путём мимо него.

**P0.3. HTTPS на реальном домене.** Прод сейчас отдаётся по HTTP (порт 80 через nginx). Через HTTP уходят JWT, пароли при логине, персональные и медицинские данные (замеры, биоимпедансометрия, фото). Поднять Caddy/Let's Encrypt (упомянуто в README как «будущее») — это не техдолг на потом, это условие выхода в прод.

**P0.4. 152-ФЗ: согласие на обработку персональных данных.** Система собирает фото клиента, фото тела «было/стало», биометрические замеры (биоимпедансометрия), женский календарь. Это чувствительные персональные данные. Нужны: экран согласия при регистрации/первом входе клиента с фиксацией факта согласия (дата, версия текста, IP/устройство), политика обработки ПДн, возможность клиента запросить выгрузку/удаление своих данных (право на отзыв согласия). Готовые черновики самих текстов согласий — см. Приложение в конце документа.
- **Конфликт «право на удаление» vs обязательный срок хранения финансовых документов.** Отзыв согласия и запрос на удаление не может распространяться на кассовые чеки, бухгалтерские документы и записи о транзакциях — их клуб обязан хранить в силу налогового законодательства (как правило не менее 5 лет), независимо от отзыва клиентом согласия на обработку персональных данных. На уровне сервиса удаления нужно явно развести: что удаляется по запросу (фото, замеры, женский календарь, контакты, привязка к маркетингу) и что помечается «обезличено, но хранится» (сами факты транзакций и чеки, см. P0.7) — тихое удаление вообще всего по одной кнопке «удалить меня» само по себе баг, который нарушит уже другой закон.

**P0.5. Хранение медиа не как data URL в БД — и весь конвейер обработки фото целиком, не только место хранения.**

**Проверено по коду, не предположение.** Фото прогресса, фото еды, фото профиля сейчас пишутся как data URL прямо в постгрес (`api/src/health/`, `ProgressPage.tsx`, `ProgressPhoto.url` в `schema.prisma` — обычный `String`). При этом:
- `api/src/main.ts` создаёт приложение (`NestFactory.create(AppModule)`) без единой настройки лимита тела запроса — ни `bodyParser`, ни `json({ limit: ... })` нигде в проекте нет. Значит действует дефолт Express/`body-parser` — **100kb на JSON-тело запроса**.
- `AddProgressPhotoDto.url` (`api/src/health/dto/health.dto.ts`) — просто `@IsString() url!: string`, без единого ограничения длины ни на бэкенде.
- На фронте (`ProgressPage.tsx`) фото берётся прямо с камеры телефона (`accept="image/*" capture="environment"`) и сразу конвертируется в data URL через `FileReader.readAsDataURL(file)` — ни ресайза, ни сжатия на клиенте нет вообще (по всему `web/src` нет ни `canvas`, ни `drawImage`, ни `toDataURL`, ни какого-либо `compress`).
- Прод по `docker-compose.prod.yml` — один контейнер `api`, без реплик, без ограничений ресурсов. Даже на целевой конфигурации (6 vCPU / 12 ГБ RAM) это по-прежнему один процесс Node.js с одним event loop на всё — лишние ядра просто простаивают, пока не сделан P3.18 (PM2 в кластерном режиме).

Практическое следствие: реальное фото с телефона «в хорошем качестве» — обычно 3–10 МБ, плюс ~37% от base64-кодирования — на два порядка больше 100kb-лимита. Скорее всего, загрузка настоящего фото уже сейчас падает с 413 у любого реального пользователя, а не только «не оптимальна». А если этот лимит когда-нибудь грубо поднимут (частый способ «починить» такую ошибку, не разобравшись в первопричине) — на многопользовательском потоке это станет отдельной проблемой: синхронный разбор JSON с многомегабайтной base64-строкой блокирует единственный event loop для вообще всех запросов в системе (не только у того, кто грузит фото) — это следствие однопоточности Node.js и не зависит от объёма RAM. Риск полного OOM от одних только фото на целевых 12 ГБ RAM (где часть делят Postgres и nginx) уже не так остр, как был бы на прежнем расчётном минимуме 4 ГБ — несколько сотен МБ одновременных тел запроса не выбьют процесс с таким запасом. Но это снижает срочность лечения именно через «больше памяти», а не отменяет саму проблему: 413-ошибка на реальном фото никуда не денется без починки лимита, а блокировка event loop бьёт по задержкам для всех пользователей независимо от того, сколько свободной RAM есть в остатке.

**Минимум, без которого реальные фото не работают на потоке клиентов (блокирует запуск):**
1. **Объектное хранилище.** Перенести хранение на S3-совместимое (Selectel S3 или MinIO на том же VPS), в БД хранить только URL — исходный смысл этого пункта.
2. **Сжатие/ресайз на клиенте перед отправкой.** В `ProgressPage.tsx` и везде, где ещё грузится фото (профиль, «было/стало», еда) — прогонять файл через canvas перед `toDataURL`/отправкой: ограничить длинную сторону (например, 1600px) и целевой размер (примерно 300–500 КБ на выходе), а не отправлять сырой файл с камеры как есть.
3. **Приём файла как multipart/бинарные данные, а не base64 в JSON.** Правильная архитектурная починка, а не заплатка поверх лимита — эндпоинт принимает `multipart/form-data` (`multer`) и грузит бинарник сразу в S3, без раздувания на 37% и без нагрузки на JSON body-parser. Явный, разумный лимит размера файла на этом эндпоинте (несколько МБ) — как страховка уже после клиентского сжатия, а не вместо него; на фронте должен быть понятный ответ пользователю при превышении («фото слишком большое, попробуйте другое»), а не молчаливый 413. **Важно согласовать лимит на обоих уровнях, не только в Node.js.** Проверено: `web/nginx.conf` (реверс-прокси `location /api/ { proxy_pass http://api:3000/api/; }`, через него и идут все запросы к API) нигде не задаёт `client_max_body_size` — значит действует дефолт nginx, 1 МБ. Сейчас это не проявляется как отдельная проблема только потому, что лимит Express (100kb) ещё меньше и срабатывает первым — но если поднять лимит на стороне API до нескольких МБ, а про nginx забыть, часть загрузок начнёт падать с 413 уже на уровне nginx, ещё не долетев до Node.js, и это будет куда труднее диагностировать (в логах API вообще ничего не будет — запрос до него не дойдёт). Оба лимита — `client_max_body_size` в `nginx.conf` и лимит на конкретном multipart-эндпоинте — задавать вместе, согласованными значениями, одним и тем же изменением.

**Что дальше, когда поток фото вырастет за пределы того, что тянет один процесс синхронно (не блокирует сам запуск, но модель данных стоит сразу спроектировать с заделом под это, чтобы потом не переделывать с нуля):**
4. **Worker Threads для тяжёлой обработки.** Серверное сжатие/ресайз (например, через `sharp`) не полагаться только на клиентское сжатие из п.2 — его можно обойти, отправив запрос к API напрямую мимо интерфейса — но выполнять его не в основном event loop, а в отдельном потоке/дочернем процессе, чтобы обработка одной тяжёлой картинки не тормозила запросы к БД от всех остальных пользователей одновременно.
5. **Асинхронная очередь на пиках (BullMQ + Redis).** Когда объём одновременных загрузок превышает то, что можно перемолоть даже воркер-потоками: сохранить файл сразу на диск/temp-хранилище, поставить задачу «сжать и загрузить в S3» в очередь, сразу ответить клиенту «файл принят, обрабатывается» — не заставляя его ждать HTTP-ответом всю обработку. Фоновый воркер разбирает очередь по одной задаче, не блокируя основное приложение. Для этого `ProgressPhoto` (и аналогичные сущности с фото) должны с самого начала (см. п.1–3) иметь поле статуса (например `status: processing | ready`), а фронт — уметь показывать плейсхолдер/спиннер, пока фото не готово, а не ожидать, что URL всегда доступен сразу после отправки. Redis — новая инфраструктурная зависимость, явно отразить в `docker-compose.prod.yml` и `DEPLOY_GUIDE.md`. На целевой конфигурации (6 vCPU / 12 ГБ RAM) запас под ещё один процесс, в отличие от прежнего расчётного минимума 4 ГБ, вполне достаточен — не блокер, но лимиты памяти на контейнер Redis в `docker-compose.prod.yml` всё равно стоит задать явно, а не полагаться на то, что «памяти и так много».

**Обязательная сверка зависимостей.** Пройтись по всем местам, где сейчас используется/задаётся `data:image` или похожий паттерн, не только в `health`-модуле (профильное фото, возможно другие места) — не оставлять один путь переделанным на S3/очередь, а второй по-старому пишущим data URL в базу.

**P0.6. Оформление клиента и абонемента на несовершеннолетнего.** Ни в модели данных, ни в API (`api/src/clients/`, `POST /clients/:id/purchase-membership`, `go-self-training`) сейчас нет понятия «несовершеннолетний клиент» — а это отдельный и более строгий контур с точки зрения 152-ФЗ и ГК РФ (ст. 26, 28 — дееспособность несовершеннолетних) и одновременно источник реального риска для клуба (ответственность за здоровье ребёнка на тренировке). Нужно:
- Поле `birthday` у `Client` (уже есть с 0.7.0) должно вычислять `isMinor` и блокировать на бэкенде, а не только в UI, всё, что несовершеннолетнему недоступно.
- **Формат тренировок только «с тренером».** `go-self-training` должен быть запрещён на уровне API для клиентов младше возрастного порога (по умолчанию 18 лет, настраиваемое значение на уровне зала/сети — некоторые клубы разрешают самостоятельные тренировки с 16). Карточка клиента при выборе даты рождения младше порога не должна давать сохраниться без выбранного тренера.
- **Законный представитель — отдельная сущность, а не обязательный `Client`.** Добавить модель `Guardian` (ФИО, телефон, email, кем приходится — родитель/опекун, подписанные согласия) с необязательной связью `linkedClientId` на уже существующего `Client`, если родитель сам тренируется в клубе. То есть: если родитель уже клиент клуба — его карточка законного представителя ссылается на существующую запись (не дублируем контакты, на ресепшене видно родство сразу). Если родитель клубом не пользуется — создаётся только лёгкая запись `Guardian` без абонемента, без входа в приложение, только с данными, нужными для согласий и связи. Оба сценария должны поддерживаться в одной форме заведения клиента, без двух разных инструментов.
- Оформление абонемента несовершеннолетнему (`purchase-membership`) должно требовать хотя бы одного `Guardian` с подписанными согласиями (152-ФЗ на ПДн несовершеннолетнего + информированное согласие на занятия, см. Приложение) прежде, чем транзакция вообще создастся — иначе это должно блокироваться на уровне сервиса, а не оставаться на совести администратора.
- `activity-log` должен фиксировать, кто из законных представителей давал согласие и когда, отдельной записью, доступной CEO.
- **Достижение 18 лет во время действия абонемента.** В день, когда `isMinor` становится `false`, система должна: разрешить клиенту самому перейти на `go-self-training`, если он этого хочет; не удалять исторические согласия законного представителя (они остаются юридическим основанием обработки данных, собранных до совершеннолетия); и явно запросить у уже взрослого клиента его собственное согласие на дальнейшую обработку — согласие родителя не может быть основанием для обработки данных совершеннолетнего человека и дальше. Без этого перехода клуб с 18-летия клиента продолжает обрабатывать его данные без действующего согласия просто потому, что никто не поменял флаг.
- **Несколько детей на одного законного представителя.** `Guardian` должен поддерживать связь с несколькими `Client` (братья/сёстры одной семьи), а не быть жёстко один-к-одному — при заведении второго ребёнка того же родителя форма должна предлагать найти уже существующего `Guardian` по телефону, а не создавать дубликат с теми же контактами.

**P0.7. Возврат оплаты (refund).** Ни в одной версии changelog нет способа отменить уже проведённый платёж — а он неизбежно понадобится: клиент ошибочно оформил не тот тариф, передумал сразу после оплаты, администратор ошибся суммой. По 54-ФЗ отмена платежа — это не «удалить транзакцию из базы», а отдельный фискальный документ «чек возврата прихода», который нужно либо пробить на кассе и отсканировать в систему тем же механизмом, что и в P0.2 (с признаком `returnOf: orderId`), либо сгенерировать через API, если реализован P0.1 (глубокая интеграция).
- Добавить `POST /orders/:id/refund` — доступно CEO/STAFF, с обязательным указанием причины.
- Откат должен явно продумываться для каждого типа `OrderLine`: возврат за абонемент — откатить продление/новую дату окончания; возврат за товар со склада — вернуть товар в остатки или списать как порчу (решить явно, а не оставлять на усмотрение реализации); возврат за шкафчик — освободить, если ещё не занят физически.
- Частичный возврат (вернули только часть группового чека — например деньги за воду, а абонемент оставили) — либо поддержать явно на уровне отдельных `OrderLine`, либо явно задокументировать, что система поддерживает только полный возврат заказа целиком, чтобы не плодить неявные промежуточные состояния.
- Отражается в `activity-log` и в отчётности CEO (P1.7) отдельной категорией, а не просто отрицательной транзакцией, которая тихо занижает выручку без объяснения причины.

**P0.8. Годовые абонементы и рассрочка — юридическая развилка, которую нужно решить до продажи такого тарифа.** Реальные клубы часто продают абонемент на 12 месяцев с оплатой не сразу целиком, а частями. Здесь есть тонкость, которую нельзя решить в коде без ответа владельца клуба: если клуб сам предоставляет клиенту рассрочку (клиент получил услугу на год вперёд, но платит частями клубу напрямую) — по сути это разновидность коммерческого кредита и в зависимости от условий может требовать иного юридического оформления, чем разовая продажа услуги. Если вместо этого клиент оформляет ежемесячное автосписание оплаты за уже оказываемые месяц за месяцем услуги (подписка, а не кредит) — это принципиально другая и куда более безопасная конструкция. Модель данных должна быть готова под любой из двух вариантов, но решение — не техническое:
- «Подписка помесячно» — `Order`/`OrderLine` из P0.2 естественно ложится на «один платёж = один месяц», просто с автосозданием следующего заказа по расписанию (когда появится P2.9 — тем же механизмом автосписания).
- «Рассрочка/кредит» — это отдельный контур с графиком платежей, привязанным к одному годовому договору, и, скорее всего, партнёрство с банком/BNPL-сервисом, а не то, что стоит реализовывать штатными средствами `Order`.
- В обоих случаях: заморозка (P2.1) на многомесячном абонементе должна корректно сдвигать не только `endDate`, но и график будущих платежей/автосписаний, если они есть — иначе заморозка и рассрочка начнут противоречить друг другу.

## Приоритет 1 — сеть из нескольких залов под одним CEO (мультилокационность)

Важное уточнение архитектуры, отдельное от «мультиарендности» из 0.1.0. Там `gymId` закладывался под сценарий «продать копию системы другому владельцу» (один CEO = один зал = один изолированный тенант). Реальная ситуация другая: **один CEO владеет несколькими залами на разных площадках**, и гости/тренеры должны свободно перемещаться между ними по единому абонементу/расписанию. Это не «ещё один Gym в базе», а отдельный уровень группировки над `Gym`, которого сейчас в модели нет вообще. Имеет смысл делать эту доработку раньше пунктов из Приоритета 2 ниже — заморозка абонемента, контроль доступа и отчётность CEO должны сразу проектироваться с учётом сети, иначе их придётся переделывать повторно.

**P1.1. Сущность «Сеть» (Network/Organization) над Gym.** Добавить модель `Network` с `ownerId` (CEO) и связью `gyms: Gym[]` — один CEO управляет одной сетью из N залов-площадок. Сейчас CEO-кабинет (`web/src/features/ceo/`, `GET /transactions`, `GET /workout-logs`) спроектирован на ровно один `gymId` — расширить до выбора конкретной точки или сводки по всей сети. См. отдельно P1.9 ниже про перенос уже существующих прод-данных — сейчас в базе уже есть реально работающий зал SiberianGym, а не чистый лист.

**P1.2. Абонемент — на уровне сети, а не одной точки.** `Client` и `MembershipPricing` сейчас привязаны к одному `gymId`. Нужно явно решить и реализовать в схеме тарифа: абонемент либо действует на всей сети по умолчанию, либо тариф явно делится на «одна точка» / «вся сеть» с разной ценой (как в реальных фитнес-сетях). Без этого клиент физически не сможет прийти во вторую точку по уже купленному абонементу — а это и есть весь смысл сети для гостя.

**P1.3. Тренер, работающий на нескольких точках.** Личное расписание тренера и персональные слоты (0.8.0) сейчас подразумевают одного тренера на одном зале. Тренер должен быть привязан к нескольким `Gym` внутри сети одновременно, а каждый персональный слот/групповое занятие — явно указывать, на какой конкретно площадке тренер физически проводит его в этот день. Календарь тренера должен показывать все точки сети без переключения контекста.

**P1.4. Инструмент CEO «Завести нового тренера».** Заведение тренера уже есть (`POST /trainers`, `POST /trainers/:id/create-login`, доступно из «Загрузки тренеров» с 0.10.0), но для реального клуба в нём не хватает полей и логики:
- **Статус занятости** — штатный сотрудник / самозанятый / ИП. Важно и для 54-ФЗ (расчёты с самозанятыми оформляются иначе, чем зарплата), и для будущего расчёта выплат тренеру.
- **Ставка/процент от тренировок** — сейчас CEO видит «выручку по тренерам» (0.10.0), но нет расчёта, сколько причитается самому тренеру с этой выручки.
- **Привязка к одной или нескольким точкам сети** (см. P1.3) — обязательное поле при заведении, а не отдельная донастройка после.
- **Специализация/направления** (тренажёрный зал, групповые программы, единоборства и т.д.) — используется фильтром в разделе «Тренер» у клиента (0.5.0).
- **Отдельное согласие самого тренера на обработку его персональных данных как сотрудника** — текст отличается от клиентского согласия (см. Приложение), фиксируется отдельно в `activity-log`.
- Результат — один инструмент, который за один проход создаёт карточку тренера, привязывает к точкам и сразу выдаёт логин, а не два отдельных действия CEO, как сейчас.
- Доступ к инструменту — только CEO; если STAFF тоже должен уметь заводить тренеров, то только в рамках своей точки, с явным ограничением в guard'е.

**P1.5. Чек-ин на любой точке сети по одному абонементу.** Пересекается с контролем доступа на входе (см. P2.2) — при проверке на ресепшене/турникете нужно валидировать не «клиент принадлежит этому `gymId`», а «абонемент клиента активен и покрывает именно эту точку сети».

**P1.6. Роли по точкам vs роли по сети.** STAFF (администратор) должен оставаться привязан к своей конкретной точке — его guard'ы не должны пускать к клиентской базе/складу/финансам другой площадки через подбор ID. CEO, наоборот, должен видеть сеть целиком и уметь фильтровать по точке. Это отдельная проверка авторизации того же типа, что уже чинили в 0.5.0 (self-service доступ клиента к чужой карточке), только на уровне «своя точка vs чужая точка сети». Отдельно проверить момент отзыва доступа: если клиента переназначили другому тренеру (0.5.0 хранит `formatHistory`), доступ старого тренера к ТЕКУЩИМ (не историческим) данным этого клиента — workout-логам, замерам, переписке — должен закрываться сразу в момент переназначения, а не оставаться по инерции старой связи.

**P1.7. Отчётность CEO: сеть целиком + разбивка по точке.** Выручка/посещаемость/занятость тренеров в кабинете CEO сейчас про один зал — нужна сводная агрегация по всей сети и переключатель/фильтр на конкретную площадку, без раздельного захода в каждую точку.

**P1.8. Физические сущности остаются привязаны к точке, а не к сети.** Шкафчики, оборудование/ППР, склад, чек-листы клининга физически существуют в конкретном здании — при переходе на модель сети важно не «расшарить» их между площадками вместе с абонементами и тренерами.

**P1.9. Миграция существующих прод-данных при введении сети.** SiberianGym — уже реально работающая на проде система с настоящими клиентами, тренерами и транзакциями, а не чистый лист для новой фичи. Когда появится `Network` (P1.1), нужен явный, протестированный на копии прод-базы migration-скрипт: создать один `Network` с `ownerId` текущего CEO и привязать к нему существующий единственный `Gym` — так, чтобы ни один существующий `Client`/`Trainer`/`Transaction` не потерял связь с данными и ни один текущий пользователь не заметил простоя. Прогонять на дампе реальной базы перед выкладкой на прод, не только на тестовых сид-данных.

**P1.10. Инструмент CEO «Завести администратора (STAFF)» и назначение/смена ролей.** Прямой пробел, которого нет вообще ни в одной версии changelog: для клиента и тренера есть `create-login` (0.8.0), а для STAFF — нет ничего, кроме единственной учётной записи CEO, которую создаёт seed-скрипт при первом развёртывании (0.1.0). Есть голый `POST /auth/users` (упомянут только в контексте исправления утечки `passwordHash` в 0.3.0) — но нигде не описано, что на нём построен CEO-интерфейс заведения администратора, и не факт, что он вообще поддерживает выбор роли, а не жёстко зашит под тот единственный сценарий, для которого был написан. Не дожидаться, пока доберётся очередь до остального Приоритета 1 — базовая многопользовательская работа нужна клубу независимо от того, готова сеть или нет.
- Симметрично P1.4 (инструмент заведения тренера): форма CEO «Завести администратора» — ФИО, контакты, привязка к одной или нескольким точкам сети (см. P1.6 — STAFF должен быть скопирован по своей точке, а не иметь доступ ко всей сети), выдача логина/временного пароля тем же паттерном, что уже есть для клиента и тренера.
- **Смена/назначение роли — отдельная развилка, которую нужно явно решить, а не оставить неявной.** Сейчас роль, судя по всему, задаётся один раз при создании учётной записи и больше не меняется никаким описанным способом. В реальности: администратора повышают до второго CEO/совладельца, тренер по факту начинает подменять администратора на ресепшене, сотрудник меняет функцию. Либо роли остаются неизменяемыми (тогда смена роли — это деактивация старой учётки, см. P3.9, и заведение новой), либо добавляется явный аудируемый `PATCH /users/:id/role` с обязательной записью в `activity-log`, кто, кому и когда сменил роль — выбрать один подход и не оставлять в проде возможность тихо получить более высокую роль через недокументированный `POST /auth/users`.
- **Множественность CEO/совладельцев.** `Network.ownerId` (P1.1) описан в единственном числе, а у реального клуба нередко несколько совладельцев, которым нужны равные права управления сетью. Явно решить: либо `ownerId` расширяется до списка, либо вводится отдельная роль «совладелец» с правами CEO, но без единоличного владения записью `Network`. В любом случае никогда не допускать состояния «в сети остался только один аккаунт с CEO-правами, и его можно деактивировать» — это прямое пересечение с P3.12 (аварийный доступ при потере входа CEO).
- Доступ к самому инструменту заведения администраторов и смены ролей — только CEO; ни один STAFF не должен иметь возможность выдать себе или кому-то ещё более высокую роль через существующие эндпоинты.

## Приоритет 2 — необходимо для операционной работы серьёзного клуба

**P2.1. Заморозка абонемента.** Стандартное ожидание клиента фитнес-клуба (болезнь, отпуск) — в модели данных и API такого действия нет вообще (`purchase-membership`, `change-tariff`, `go-self-training` — есть, заморозки нет). Добавить `POST /clients/:id/freeze-membership` с продлением даты окончания на число дней заморозки, лимитом заморозок по тарифу, отражением в `activity-log`.

**P2.2. Контроль доступа на входе.** Ни в одной версии нет способа физически пустить клиента в зал, кроме как «на глаз» администратором. Для клуба с потоком нужен хотя бы QR-код/штрихкод в приложении клиента, который сканирует администратор (или интеграция с турникетом/СКУД) — с проверкой активности абонемента в реальном времени и записью прохода. См. P1.5 про валидацию на конкретной точке сети. Отдельно предусмотреть дебаунс: клиент по ошибке сканирует QR на входе дважды подряд за несколько секунд — нужно игнорировать повторный скан того же клиента в течение короткого окна после успешного прохода, иначе в логе прохода задваиваются записи и путается статистика посещаемости (P1.7).

**P2.3. Лист ожидания на групповые занятия.** Сейчас `schedule` поддерживает только запись/отмену — при заполненном занятии клиент просто не может записаться. Нужен waitlist с автоматическим уведомлением при освобождении места.

**P2.4. Push/SMS-напоминания о записи.** Явка была намеренно ограничена email (0.1.0), но email плохо работает как напоминание «через час тренировка» — это снижает посещаемость и увеличивает no-show. Минимум: Web Push через уже подключённый service worker (PWA уже есть — push не хватает только реализации), в идеале — SMS как fallback для критичных напоминаний (отмена/перенос тренером).

**P2.5. Политика no-show / отмены.** Персональные слоты и групповые занятия можно отменить, но нет окна «поздняя отмена» (например, за 12 часов) и нет логики штрафа/списания при неявке — для клуба с платными персональными тренировками это прямая потеря денег тренера/клуба.

**P2.6. Пробное посещение / гостевой доступ для лидов.** Вся система рассчитана на уже существующего клиента с абонементом. Нет сущности «лид/гость», нет пробного дня/пробной тренировки, нет воронки от «пришёл узнать» до «купил абонемент» — а это стандартный канал продаж для клуба. Нужен минимум: гостевая карточка с датой визита и статусом конверсии.

**P2.7. Защита от двойного бронирования.** Проверить и явно покрыть тестами: пересечение персональных слотов одного тренера (в том числе между разными точками сети — см. P1.3), двойная аренда одного шкафчика, овербукинг группового занятия сверх вместимости зала.

**P2.8. Система централизованного управления шкафчиками (опционально, включается флагом на точке).** Альтернатива нынешней ручной аренде шкафчика (0.4.0: `Locker` — аренда с транзакцией по цене за день, освобождение вручную) для точек, где физически установлено оборудование: вместо дорогого считывателя на каждой дверце — один терминал-киоск со сканером QR-кодов на всю раздевалку или на отдельный ряд шкафчиков.

- **Переключатель режима, а не замена.** Добавить на уровне `Gym` (физическое оборудование привязано к точке, а не к сети — см. P1.8) настройку `lockerMode`: `manual` (текущий, по умолчанию) | `centralized_kiosk`. Большинство точек сети физически не будет оснащено такой системой — ручной сценарий аренды должен продолжать работать без изменений там, где флаг выключен; существующие эндпоинты `lockers` ломать нельзя.
- **Клиентский сценарий:**
  1. Клиент получает QR — разумно переиспользовать тот же QR, что для чек-ина на входе (P2.2/P1.5), а не заводить второй.
  2. Подносит QR к сканеру терминала.
  3. Бэкенд резолвит: если за клиентом уже закреплён шкафчик по текущей аренде — возвращает его номер повторно (идемпотентно, повторный скан не назначает новый шкафчик, пока текущий не освобождён); если нет — находит свободный `Locker` этой точки и назначает.
  4. Терминал показывает номер («Ваш шкафчик №42»), отправляет сигнал открытия на конкретную дверцу через сетевой контроллер.
  5. Дверца щёлкает и приоткрывается за счёт пружинного толкателя в электронном замке (соленоидном/моторном), клиент кладёт вещи и захлопывает — замок блокируется механически, состояние двери (открыта/закрыта) читается с датчика в замке.
  6. Для получения вещей — повторный скан того же QR на терминале → шкафчик открывается → после закрытия аренда закрывается, шкафчик освобождается для следующего гостя.
- **Расширение модели `Locker` (0.4.0).** Добавить поля: `controllerId`, `channelNumber` (какой релейный выход на контроллере отвечает за конкретную дверцу), `doorSensorState` (open/closed, обновляется по колбэку от контроллера), `assignedClientId`/`assignedAt`, `bankId`/`zone` — если шкафчики физически разбиты на ряды, каждый ряд может висеть на своём контроллере (обычно один контроллер держит 12, 24 или 36 замков).
- **API:** `POST /lockers/kiosk/scan` — вызывается терминалом при скане QR: резолвит клиента, ищет/возвращает шкафчик, инициирует сигнал открытия, пишет событие в `activity-log`. `POST /lockers/kiosk/release` — тот же принцип на выдачу вещей. Отдельный вебхук/колбэк от контроллера на изменение состояния двери нужен, чтобы отличить «клиент забрал вещи и закрыл дверцу» от «дверца не закрылась» — второе не должно тихо считаться свободным местом, а должно уходить администратору.
- **Слой абстракции над оборудованием.** Не завязывать бизнес-логику напрямую на протокол одного производителя (в описании процесса упомянут Kerong как самый популярный бренд электронных защёлок со встроенным датчиком состояния дверцы для таких систем) — завести интерфейс `LockerControllerDriver` с методами вроде `open(channel)` / `getStatus(channel)`, чтобы при смене поставщика контроллеров подставлялась другая реализация драйвера, а не переписывалась логика назначения шкафчиков.
- **Обработка отказов.** Нет свободных шкафчиков на точке — терминал явно показывает это клиенту, а не зависает. Контроллер не ответил на команду открытия — терминал показывает «обратитесь к администратору», попытка логируется, шкафчик не считается занятым. Дверца не закрылась в течение N минут после разблокировки — алерт администратору через тот же канал уведомлений, что и в P3.7.
- **Не блокирует остальной бэклог.** Пункт полностью опционален и не блокирует ни Приоритет 0, ни остальной Приоритет 2 — реализуется на конкретной точке после того, как клуб физически закупит и смонтирует терминал и замки. В бэклог его стоит внести уже сейчас ради одного: чтобы модель `Locker` с самого начала проектировалась с этими полями как расширяемая, а не переписывалась с нуля в день установки первого терминала.

**P2.9. Самостоятельная безналичная оплата в приложении (эквайринг без участия администратора).** Раньше это было в Приоритете 0 как «блокер запуска» — на самом деле нет: P0.1+P0.2 уже дают легальный и надёжный способ принимать деньги через администратора (наличные или карта на физическом терминале — с точки зрения софта это один и тот же сценарий «оплата на ресепшене + скан чека»). Этот пункт про другое — про то, чтобы клиент мог оплатить продление абонемента из дома, не приходя в клуб и не отвлекая администратора. Это реальная операционная потребность растущего клуба (см. рассуждение из старого P0.2 про «администратор физически не масштабируется на поток»), но не условие открытия дверей в первый день.
- Добавить хотя бы один провод эквайринга (Альфа-Банк, как и планировалось в 0.1.0) с приёмом карты прямо в приложении клиента и автоматическим статусом оплаты.
- Встраивается в уже описанную в P0.2 механику `Order`: успешная оплата от банка переводит `Order` сразу в `paid`, без сканирования чека — сам чек в этом случае обязателен по 54-ФЗ так же, как и при наличных, но его должен выдать сам платёжный шлюз/встроенная в эквайринг онлайн-касса, а не администратор вручную.
- Пока этот пункт не реализован — кнопка «Оплатить картой онлайн» в приложении клиента просто не показывается, доступен только вариант «Оплатить наличными администратору» из P0.2. Это осознанное и допустимое ограничение MVP, а не недоделанность.

**P2.10. Переназначение подопечных при уходе/отпуске тренера.** Ни в одной версии нет группового инструмента на случай, когда тренер увольняется или уходит в длительный отпуск: у него на руках может быть много активных подопечных (карточка тренера показывает «подопечные, платежи» — 0.8.0) и запланированные персональные слоты на недели вперёд. Нужен инструмент CEO/STAFF: отметить тренера временно недоступным (диапазон дат) или окончательно ушедшим, массово перенести/отменить его будущие персональные слоты с уведомлением клиентов (P2.4), и либо переназначить подопечных на другого тренера пакетно, либо перевести на самостоятельные тренировки — вместо того чтобы администратор вручную разбирал это по одному клиенту.

**P2.11. Контроль срока действия сертификатов тренеров.** `trainers.findAll` уже отдаёт сертификаты в карточке тренера (0.5.0), но нет ни поля срока действия, ни какого-либо контроля. Для серьёзного клуба это не только данные для профиля — это ответственность и часто требование страховки клуба: тренер с истёкшим сертификатом не должен тихо продолжать вести групповые/персональные занятия. Добавить `expiresAt` к сертификату, алерт CEO за N дней до истечения (тот же канал, что в P3.7), и — по решению владельца — блокировку записи новых персональных слотов к тренеру с истёкшим обязательным сертификатом.

**P2.12. Автогенерация регулярного расписания групповых занятий.** Сейчас групповое занятие создаётся администратором вручную на конкретную дату (0.3.0: «создание, запись клиента, отмена»). Реальный клуб проводит одни и те же занятия (например, йога по вторникам и четвергам в 19:00) многие месяцы подряд — без генератора повторяющихся занятий администратор либо создаёт их вручную на много месяцев вперёд, либо (более вероятный сценарий бага) забывает создать занятие на следующую неделю, и клиенты, ожидающие привычное расписание, натыкаются на пустой календарь. Добавить шаблон повторения (еженедельно по дням недели, с датой начала/конца серии) с автогенерацией конкретных occurrence-занятий вперёд на настраиваемый горизонт (например, всегда на 4 недели вперёд), и явно продумать, что происходит с уже существующими записями клиентов при редактировании или отмене всей серии целиком.

## Приоритет 3 — техническая надёжность (то, что обычно спрашивает сеньор на ревью)

**P3.1. Автоматические тесты.** Во всём changelog проверка — это ручной сквозной сценарий в браузере/через curl с последующей очисткой тестовых данных. Для 21+ бизнес-модуля это не масштабируется и не защищает от регрессий. Добавить хотя бы: unit-тесты на сервисы с денежной логикой (транзакции, тарифы, склад/инвентаризация со списанием по FIFO, сверка сумм заказа и чека из P0.2), e2e на критичные сценарии (вход, покупка абонемента, запись на занятие, проверка владения/авторизации по ролям — особенно потому что дыры авторизации уже находили и чинили вручную, см. 0.5.0).

**P3.2. CI/CD.** Нет упоминания пайплайна — сборка и тесты гоняются вручную локально. Добавить GitHub Actions/GitLab CI: lint + typecheck + тесты + сборка Docker-образов на каждый PR, деплой по тегу.
- **Нет отдельного стенда (staging) и нет бесшовного деплоя.** В репозитории только один compose-файл на прод (`docker-compose.prod.yml`), без аналога для промежуточного стенда — новые версии впервые проверяются сразу на реальных данных клуба. `docker compose up -d --build` при деплое пересоздаёт контейнер `api` (а с P3.18 — весь кластер PM2 внутри него) — это кратковременный простой при каждом обновлении, не бесшовный rolling/blue-green деплой. Для клуба с реальным потоком клиентов стоит завести хотя бы дешёвый staging (второй такой же VPS меньшей конфигурации или тот же сервер с отдельным портом/поддоменом) для проверки перед реальным продом, и рассмотреть бесшовный деплой (например, через несколько реплик `api` за nginx с поочерёдным перезапуском) не как обязательное на старте, а как следующий шаг после того, как P3.18 и P3.2 уже сделаны.

**P3.3. Бэкапы БД и план восстановления.** Проверено дословно по `DEPLOY_GUIDE.md`: единственная описанная процедура — вручную выполнить `pg_dump` в SSH-сессии и «время от времени» самому скачать файл к себе на компьютер через `scp`/WinSCP. Ни cron, ни автоматизации, ни ротации/удаления старых копий, ни разу проверенного восстановления — нет вообще, это полностью ручной процесс, зависящий от того, вспомнит ли человек его запустить. При потере диска клуб теряет всю финансовую историю, клиентскую базу и медицинские данные разом, если между последним ручным бэкапом и инцидентом прошло много времени. Настроить регулярный автоматический `pg_dump` по cron (или `pgBackRest` для инкрементальных копий на большем объёме данных) в объектное хранилище (тот же S3 из P0.5, не на компьютер конкретного человека) с автоматической ротацией/удалением старых копий по сроку хранения и хотя бы раз протестированным полным восстановлением на отдельном сервере — не просто «бэкап есть», а «бэкап проверенно разворачивается и открывается».

**P3.4. Rate limiting и защита логина от перебора.** `POST /auth/login` не упомянут как защищённый от брутфорса — добавить троттлинг (например `@nestjs/throttler`) и блокировку/капчу после N неудачных попыток.
- **Это защита только логина, а не всего API.** Проверено: `web/nginx.conf` раздаёт только статику фронтенда (`limit_req` там нет), `DEPLOY_GUIDE.md` настраивает только `ufw` (блокировка портов, а не запросов) — общего троттлинга или защиты от сканирования/сетевого шторма на сам API нигде не настроено, кроме предлагаемого здесь ограничения именно на `/auth/login`. Минимум — общий rate limit через тот же `@nestjs/throttler` на все эндпоинты, а не только логин. Отдельно — осознанное решение (не обязательно перед первым запуском, но не должно остаться «никогда не думали об этом»): ставить ли перед сервером бесплатный слой вроде Cloudflare — снимает большую часть сетевого шторма ещё до того, как трафик вообще доходит до VPS.

**P3.5. Самостоятельный сброс пароля.** Сейчас пароль клиенту/тренеру выдаёт администратор вручную (`create-login`). Забыл пароль — значит идти к администратору. Добавить flow «забыли пароль» через email.

**P3.6. 2FA для CEO/STAFF.** Аккаунты с доступом к финансам и медицинским данным всех клиентов стоит защитить вторым фактором, хотя бы TOTP.

**P3.7. Мониторинг и алерты.** Нет health-check эндпоинта, нет трекинга ошибок (Sentry, GlitchTip или аналог), нет алертов при падении API/контейнера. Добавить `GET /health`, подключить error tracking (Sentry или самохостимый GlitchTip, если не хочется платного SaaS), настроить хотя бы простейший uptime-мониторинг — внешний сервис (UptimeRobot) или самохостимый (Uptime Kuma), с проверкой `/health` раз в 30–60 секунд.
- **Ресурсы сервера — отдельный канал алертов, не только доступность API.** Сейчас нет вообще ничего, что следило бы за состоянием самого VPS, а не только за тем, отвечает ли API. Поднять агент — Netdata (разворачивается одной командой, есть готовая интеграция с Telegram) либо Prometheus + Grafana / Zabbix (тяжелее в настройке, но привычнее, если уже есть опыт) — с порогами: CPU > 85%, RAM > 90%, свободное место на диске < 15% — уведомление сразу в Telegram/Slack, а не постфактум, когда сервис уже упал. Прямо стыкуется с уже отмеченными рисками: диск может забиться логами контейнеров (P3.16), а рост потребления RAM без возврата — первый видимый симптом утечки памяти (P3.17) задолго до того, как сработает `OOM Killer` и процесс просто убьёт.
- **Пагинация журнала изменений — частный случай общей проблемы.** `GET /api/activity-log` в тестовом сценарии 0.10.0 проверялся на 29 записях — за 12 месяцев работы реального клуба это тысячи и десятки тысяч записей. Без пагинации и фильтров по дате/модулю/пользователю этот эндпоинт со временем либо станет практически бесполезным для CEO (нереально пролистать), либо начнёт отдавать ответы, которые кладут фронтенд или сам API по памяти. См. P3.20 — та же проблема системно у большинства списковых эндпоинтов, не только здесь.
- **Алерты по просроченному обслуживанию и товарам с истекающим сроком годности.** ППР оборудования (0.3.0) считает следующую дату обслуживания автоматически, но если никто не отметил его выполненным — оборудование молча продолжает числиться «на обслуживании» без предупреждения; склад хранит партии по сроку годности (0.3.0) для целей списания постфактум, но не предупреждает заранее, что скоро что-то просрочится. Оба случая — молчаливые риски (травмоопасное оборудование, продажа просроченной воды/еды клиенту), которые должны попадать в тот же канал алертов, что и технические инциденты.

**P3.8. Управление сессиями.** Нет отзыва токенов при смене пароля/увольнении сотрудника — если у уволенного администратора был JWT, он валиден до истечения срока жизни токена. Проверено: `JWT_EXPIRES_IN_SECONDS: 604800` в `docker-compose.prod.yml` — это ровно 7 суток, то есть уволенный сотрудник теоретически сохраняет рабочий доступ ко всей системе (включая клиентские данные и финансы, в зависимости от роли) вплоть до недели после увольнения, если токен не отозван никаким другим способом. Добавить хотя бы серверный список отозванных токенов или короткий TTL + refresh-токен с возможностью инвалидации.

**P3.9. Деактивация сотрудника без потери истории.** В системе есть `create-login` для выдачи доступа тренеру/клиенту, но нет обратного действия — способа корректно закрыть доступ уволенному тренеру или администратору. Просто удалить `User` нельзя — на него ссылаются исторические `workout-logs` (`assignedBy: trainer`), записи `activity-log`, программы клиентов. Нужен статус `active`/`deactivated` на аккаунте сотрудника: деактивированный логин не может войти сразу, независимо от TTL токена (см. P3.8), но вся история действий и авторства остаётся читаемой и не превращается в битые ссылки на несуществующего пользователя.

**P3.10. Гонки при назначении ограниченных ресурсов (TOCTOU).** Несколько мест в системе следуют одному и тому же шаблону «проверить, что ресурс свободен → затем его занять» двумя отдельными операциями: назначение шкафчика в централизованном киоске (P2.8), проверка вместимости группового занятия и пересечения персональных слотов тренера (P2.7), поиск свободного `Locker` при обычной ручной аренде (0.4.0). При одновременном обращении двух клиентов/терминалов в один и тот же момент это классическая гонка: оба «видят» ресурс свободным до того, как кто-то из них успевает его занять, и оба его получают — овербукинг занятия сверх вместимости, два клиента с одним и тем же шкафчиком. Нужна проверка и занятие ресурса в одной транзакции БД с соответствующим уровнем изоляции или уникальным ограничением на уровне схемы (например, уникальный индекс на «активная бронь на этот `Locker`/слот»), а не проверка в коде сервиса с последующей отдельной записью.

**P3.11. Часовые пояса и граничные даты в расчётах.** Клуб фактически работает в конкретном часовом поясе (для SiberianGym — Азия/Новосибирск), а сервер и Postgres по умолчанию скорее всего работают в UTC. Даты окончания абонемента, заморозки (P2.1), просрочки оборудования и склада (P3.7), статистика посещаемости «по дням» (0.10.0) — везде, где дата используется как «конец дня» или «сегодня», нужно явно считать по часовому поясу зала/сети (учитывая, что в мультилокационной сети из Приоритета 1 разные точки в теории могут быть в разных часовых поясах), а не по UTC-полуночи сервера — иначе абонемент клиента истечёт на несколько часов раньше или позже, чем клиент ожидает, в зависимости от того, до или после обеда сейчас у сервера в UTC.

**P3.12. Аварийный доступ при потере входа единственным CEO.** В зале/сети обычно один аккаунт CEO. Если он теряет доступ (забыл пароль до появления самостоятельного сброса из P3.5, потерял устройство с 2FA после P3.6) — нужна заранее продуманная процедура восстановления (например, сброс через прямой доступ к базе с обязательной записью в `activity-log` о том, что доступ восстановлен вручную, и обязательной сменой пароля/2FA сразу после), а не «звонить разработчику, чтобы он полез в базу руками без всякого следа». Это тот сценарий, который не проявится в тестировании, но выключит управление всем залом/сетью в реальности ровно тогда, когда он случится.

**P3.13. Реальный N+1-запрос в `finalizeInventory` (`api/src/stock/stock.service.ts`).** Проверено по коду, не гипотеза: метод делает `for (const e of dto.entries) { await this.prisma.stockBatch.findMany(...) }` — отдельный запрос к БД на каждую позицию инвентаризации, последовательно, внутри цикла. При инвентаризации склада из, например, 100 товарных позиций это 100 последовательных round-trip'ов к Postgres вместо одного сгруппированного запроса. Это не системная проблема всего проекта — рядом проверенные сервисы (например, лидерборд в `workout-logs.service.ts`) корректно используют `include`/`findMany` одним запросом, — а конкретный локальный баг: получить сразу все нужные `stockBatch` одним запросом (`findMany` по списку `catalogItemId`+`location` из `dto.entries`), сгруппировать результат в памяти. Заодно проверить остальные места, принимающие на вход массив позиций, на тот же паттерн — этот нашёлся при целевой проверке, не факт, что единственный в проекте.

**P3.14. Пул соединений Prisma не настроен явно, индексы не проверены под реальным объёмом данных.** `DATABASE_URL` в `.env.prod.example` не содержит `connection_limit` — значит действует дефолт Prisma (число физических ядер × 2 + 1). На целевой конфигурации (6 vCPU) это около 13 соединений — заметно просторнее, чем было бы на прежнем расчётном минимуме 2 vCPU (~5), так что degradация от одной лишь нехватки соединений менее вероятна на старте. Но дефолтная формула считает физические ядра ВСЕЙ машины, а не то, что реально нужно API под конкретную нагрузку — она не подстроена ни под P3.18 (если PM2 поднимет 5–6 инстансов API в кластере, каждый со своим Prisma-клиентом и своим дефолтным пулом, дефолт по формуле умножится на число инстансов и может неожиданно приблизиться к типичному потолку Postgres в 100 соединений), ни под то, что Postgres на этой же машине тоже не бесплатен по соединениям. Значение стоит задать явно и осознанно, а не полагаться на дефолт, который меняет смысл в зависимости от того, сколько процессов API реально поднято. `PrismaService` (`api/src/prisma/prisma.service.ts`) — корректный NestJS-singleton с `$connect`/`$disconnect` в хуках жизненного цикла, так что это не «забыли закрыть соединение» в буквальном смысле (Prisma сама управляет пулом, разработчик не открывает/закрывает соединения вручную), а узкое место пропускной способности: лишние запросы просто встают в очередь, и при пиковой нагрузке это проявляется как рост задержек и таймауты у части пользователей, а не как явная ошибка в логах. Отдельно: в `schema.prisma` уже есть 32 индекса (`@@index` на `gymId`/`clientId`/`trainerId`, несколько `@@unique`) — типовой сценарий «выбрать всё по клубу/клиенту/тренеру» закрыт, но ни один составной индекс под конкретные горячие запросы (например, «расписание точки за диапазон дат» — фильтр сразу по `gymId` и диапазону дат) не проверен на плане выполнения (`EXPLAIN ANALYZE`) с объёмом данных, приближенным к реальному, а не к десяткам тестовых записей. Ни то, ни другое нельзя окончательно подтвердить чтением кода — нужен реальный прогон под нагрузкой (P3.20) с донастройкой по его результатам.

**P3.15. Тяжёлая синхронная агрегация в рейтинге тренировок блокирует event loop для всех пользователей разом.** `WorkoutLogsService.leaderboard()` (`api/src/workout-logs/workout-logs.service.ts`) забирает ВСЕ записи тренировок клуба за период одним `findMany` с вложенными `include` (упражнения → подходы), без пагинации и без ограничения объёма, а затем построчно и синхронно, прямо в обработчике запроса, регулярными выражениями разбирает строки вида «80 кг» и «8-12» на каждый подход каждой тренировки, суммирует и сортирует в памяти JavaScript. На тестовых объёмах незаметно; на горизонте 6–12 месяцев активного клуба (тот же горизонт, что уже используется в этом документе как критерий проверки) это может стать заметной по времени синхронной работой, которая на время выполнения блокирует обработку вообще всех остальных запросов от всех остальных пользователей — тот же класс проблемы, что уже отмечен для сжатия фото в P0.5, только источник другой. Чинить так же: считать агрегат средствами самой БД (SQL-агрегация вместо разбора строк в JS) или кэшировать посчитанный рейтинг с периодическим фоновым пересчётом, а не заново вживую на каждый запрос лидерборда.

**P3.16. Логи контейнеров ничем не ограничены — риск заполнения диска со временем.** В `docker-compose.prod.yml` не задана секция `logging` ни для одного сервиса — действует дефолтный Docker-драйвер `json-file` без ограничения размера. Собственных вызовов логирования в самом API немного (всего несколько мест с `Logger`/`console.log` во всём `api/src`), так что источник риска не «приложение слишком много логирует», а именно неограниченный лог-файл контейнера на уровне Docker. На целевых 120 ГБ NVMe (вместо прежнего расчётного минимума 40–60 ГБ) это займёт заметно больше времени, чем на минимальной конфигурации — и с учётом того, что медиа теперь уезжают на отдельный S3 (P0.5), а не копятся в той же БД на этом диске, локальный диск в основном остаётся под Postgres, логи и временные файлы очереди (P0.5, п.5). Но «займёт больше времени» — это отсрочка, а не защита: неограниченный рост рано или поздно всё равно упрётся в лимит, просто позже, и без явного алерта на диск (см. P3.7) момент будет замечен не заранее, а по факту аварийной остановки Postgres. Починка — та же самая явная секция на каждый сервис в `docker-compose.prod.yml`, независимо от того, сколько места есть в запасе:
```yaml
logging:
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "5"
```
Плюс мониторинг свободного места на диске как отдельный алерт в дополнение к P3.7 (там сейчас про падение API/контейнера, но не про диск). Заодно — мелкая, но накопительная гигиена самой ОС, которой сейчас в `DEPLOY_GUIDE.md` нет вовсе: регулярная очистка `/tmp` (актуально вдвойне, если появится временное хранение файлов для очереди из P0.5, п.5) и кэша пакетов (`apt clean`) — по отдельному cron-задаче или systemd-таймеру, не полагаясь на то, что кто-то вспомнит зайти и почистить руками.

**P3.17. Утечки памяти Node.js — по коду не найдено, но и не подтверждено, а не одно и то же.** Целевая проверка по `api/src` не нашла ни забытых `setInterval`/`setTimeout` без очистки, ни `process.on`/подписчиков на события без отписки, ни синхронных блокирующих вызовов вроде `readFileSync`/`execSync` — ни одного из типичных источников утечки или блокировки event loop. Это честный, но ограниченный результат: статическое чтение кода в принципе не может подтвердить отсутствие утечки — она проявляется только на графике потребления памяти процессом за часы/дни реальной работы (например, после сотен циклов создания/сборки мусора объектов при большом потоке запросов). На целевых 12 ГБ RAM (вместо прежнего расчётного минимума 4 ГБ) это даже более актуально, не менее: с большим запасом медленная утечка будет копиться дольше, прежде чем упрётся в лимит и станет заметной по симптомам — соответственно soak-тест в P3.20 должен быть рассчитан на достаточную длительность, а не на короткий прогон, который на такой машине скорее всего просто не успеет показать рост. Не заводить это как отдельную «работу по коду» — единственный осмысленный способ проверить фактически описан в P3.20.

**P3.18. Процесс-менеджер (PM2, кластерный режим) вместо прямого `node dist/main.js`.** Проверено по коду: `api/Dockerfile` запускает процесс напрямую — `CMD ["sh", "-c", "npx prisma migrate deploy && node dist/main.js"]`, без какого-либо менеджера процессов. Это означает два отдельных риска:
- **Используется только одно ядро CPU из выделенных.** Node.js однопоточный для выполнения JS-кода (см. также P3.15, P3.17 про блокировку event loop) — на целевой конфигурации (6 vCPU) это означает, что под нагрузкой задействуется примерно 1/6 реальной вычислительной мощности сервера, а остальные пять ядер простаивают. Это даже более заметный разрыв, чем был бы на прежнем расчётном минимуме 2 vCPU (там простаивала «только» половина) — чем больше ядер на сервере, тем дороже стоит не использовать кластерный режим.
- **Падение процесса — это простой, а не мгновенное восстановление.** `restart: unless-stopped` в `docker-compose.prod.yml` в итоге перезапустит упавший контейнер, но не мгновенно и не бесшовно — все, кто был подключён в момент падения, получат обрыв, а новые запросы будут отклоняться, пока контейнер не поднимется заново.

Починка — заменить прямой запуск на PM2 в кластерном режиме внутри того же контейнера `api` (`pm2-runtime start dist/main.js -i max`, либо явное число инстансов — на целевых 6 vCPU разумно 5, оставляя одно ядро под Postgres/nginx/фоновые процессы, а не выбирать `max` не глядя). PM2 поднимает несколько копий процесса, распределяет входящие соединения между ними и мгновенно перезапускает конкретно упавшую копию, не затрагивая остальные — падение одного запроса не превращается в простой всего сервиса. Два момента, которые нужно явно учесть при переходе на кластер, а не только включить его:
- Проекта не использует WebSocket (обычный REST), так что sticky-сессии между инстансами не нужны; JWT сам по себе не хранит состояние на сервере, так что авторизация с кластеризацией не конфликтует.
- **Миграции должны остаться разовым шагом до форка кластера, а не повторяться на каждый инстанс.** Сейчас `CMD` в `api/Dockerfile` — `npx prisma migrate deploy && node dist/main.js`. При переходе на PM2 команда должна стать `npx prisma migrate deploy && pm2-runtime start dist/main.js -i 5` (или аналог) — то есть миграции по-прежнему выполняются один раз, ДО того, как PM2 форкнёт несколько процессов, а не отдельно в каждом из них (иначе несколько параллельных `migrate deploy` могут столкнуться друг с другом на блокировке миграционной таблицы). Явно проверить это при реализации, не полагаясь на то, что само сложится правильно.
- Если будет реализован P3.8 (отзыв токенов у уволенных/сменивших пароль), список отозванных токенов обязан жить в общем хранилище (БД или Redis — тот же Redis может появиться из P0.5, если дойдёт до очереди BullMQ), а не в памяти одного процесса — иначе отзыв токена в памяти инстанса №1 не подействует на инстансы №2–4, и уволенный сотрудник сможет продолжить работать через любой из них, на который его запрос попадёт по балансировке PM2.

**P3.19. Пагинация — не только у журнала изменений, а системно у большинства списковых эндпоинтов.** P3.7 уже отмечает проблему для `activity-log`; целевая проверка показала, что это не единичный случай — из 17 сервисов, использующих `findMany`, явный лимит (`take`) задан только в двух (`activity-log.service.ts`, `stock.service.ts`). В частности, без пагинации и с глубокими вложенными `include` разом возвращают весь объём данных клуба:
- `ClientsService.findAll()` — все клиенты клуба одним ответом, с `membership`, `trainer`, `formatHistory`.
- `TrainersService.findAll()` / `findMyClients()` — все тренеры клуба и все клиенты одного тренера, с вложенными связями.
- `ScheduleService` — списки `groupClass`/`personalSlot` (нужно отдельно проверить, ограничены ли они хотя бы диапазоном дат — если нет, тот же риск).
- `WorkoutLogsService.listAll()` — уже отмечен в P3.15 как источник блокировки event loop, но это и источник неограниченного по объёму ответа тоже.

На клубе с одной-двумя сотнями активных клиентов пока не критично; на объёме в несколько сотен/тысяч — особенно в сети из Приоритета 1, где счёт клиентов идёт по всей сети сразу, а не по одной точке — это растущий с каждым месяцем ответ, который не только медленнее отдаётся, но и дольше держит event loop на сериализации (та же природа проблемы, что в P3.15). Добавить `LIMIT`/`OFFSET` (в Prisma — `take`/`skip`, либо курсорная пагинация через `cursor` для длинных списков, чтобы не «плыла» страница при параллельных изменениях данных) на каждый списковый эндпоинт с разумным дефолтом (20–50 записей на страницу) и явным параметром страницы в query — и синхронно поправить фронтенд под постраничную загрузку/подгрузку вместо ожидания одного большого ответа целиком.

**P3.20. Нагрузочное и soak-тестирование перед реальным запуском — отдельный обязательный шаг, не факультатив.** Единственная зафиксированная в CHANGELOG практика проверки — ручной сквозной сценарий одним пользователем (раздел «Проверено» на каждую версию). Это в принципе не может обнаружить ни один из пунктов P3.13–P3.19 выше, ни реальное поведение при 50–100 одновременных пользователях, ни то, как система себя ведёт, когда часть из них одновременно грузит фото (P0.5). Перед приёмом первых реальных платежей — прогнать против копии прод-окружения (не самого прода) нагрузочный тест инструментом вроде `k6` или `autocannon`: сценарий с N параллельными «пользователями», часть из которых одновременно загружает фото, часть — читает расписание/лидерборд, часть — оформляет заказы (P0.2). Смотреть не только на факт падения/непадения, а на: потребление RAM процессом `api` в динамике (рост без возврата — признак утечки, см. P3.17), задержки ответов под нагрузкой по мере роста числа параллельных запросов, фактическое число одновременных соединений к Postgres против настроенного пула (P3.14), и — раз теперь в кластере несколько копий (P3.18) — что нагрузка действительно распределяется между всеми инстансами, а не бьёт в один. Результат прогона — основание для конкретных цифр в P3.14, а не гадание. Держать этот тест как повторяемый скрипт в репозитории, а не разовый ручной прогон, чтобы гонять его снова после значимых изменений — тем же принципом, что уже заложен для остального техдолга в этом документе.

**P3.21. Postgres работает на полностью дефолтных настройках, независимо от объёма выделенной RAM.** Проверено: `docker-compose.prod.yml` поднимает `postgres:16-alpine` без единого переопределения (`command:`, смонтированного `postgresql.conf`) — значит действуют дефолты образа: `shared_buffers` около 128 МБ, `work_mem` 4 МБ, `maintenance_work_mem` 64 МБ — рассчитанные на минимальную, а не на выделенную под задачу машину. На целевой конфигурации (12 ГБ RAM, из которых Postgres может уверенно использовать несколько гигабайт) это означает, что база не использует доступную память там, где могла бы держать данные в собственном разделяемом буфере вместо повторного чтения с диска, и не может эффективно применять `maintenance_work_mem` при `VACUUM`/переиндексации больших таблиц. Прогнать реальные параметры (12 ГБ RAM, 6 vCPU, NVMe, `db_type: web` для OLTP-нагрузки) через PGTune (pgtune.leopard.in.ua или аналог), полученные значения передать образу через `command: postgres -c shared_buffers=... -c work_mem=...` в `docker-compose.prod.yml` либо смонтированным файлом `postgresql.conf`. `autovacuum` включён по умолчанию в самом Postgres (никто явно не отключал) — но дефолтные пороги автовакуума тоже рассчитаны не под реальный объём записей активного клуба, донастроить вместе с остальным тюнингом, а не отдельным пунктом позже.

**P3.22. Нет глобальных обработчиков необработанных ошибок — процесс падает «молча», без диагностируемого следа.** Проверено: во всём `api/src` нет ни одного `process.on('uncaughtException', ...)`, ни `process.on('unhandledRejection', ...)`, ни глобального NestJS `ExceptionFilter` (`@Catch`/`app.useGlobalFilters`). Любая необработанная ошибка — самый частый способ, которым Node.js-процесс падает, — сейчас никак не логируется перед падением, только стандартное сообщение в stdout контейнера. P3.18 (PM2) чинит следствие: процесс быстро перезапустится, — но не даёт понять, почему он упал, если это происходит не у вас на глазах. Добавить: глобальный NestJS `ExceptionFilter`, логирующий полную ошибку (стек, путь запроса) перед тем, как вернуть клиенту аккуратный 500 без деталей реализации; и на уровне процесса — обработчики `unhandledRejection`/`uncaughtException`, которые пишут ошибку в лог (а с P3.7 — сразу улетают в error tracking) перед тем, как дать PM2 перезапустить процесс, а не проваливаться в тишину.

**P3.23. Отправка email не имеет явного таймаута и блокирует ответ клиенту, ожидая её завершения.** `EmailService.send()` (`api/src/email/email.service.ts`) вызывает `await this.transporter.sendMail(...)` без явных `connectionTimeout`/`greetingTimeout`/`socketTimeout` у `nodemailer.createTransport()` — действуют дефолты библиотеки, которые могут ждать медленный/недоступный SMTP-сервер по несколько минут. Сам вызов устойчив с точки зрения бизнес-логики (обёрнут в `try/catch`, сбой отправки не роняет операцию) — но `await` перед ним означает, что HTTP-ответ администратору (например, при `createLogin`) не вернётся, пока `sendMail` не завершится одним из двух способов: успехом или таймаутом библиотеки по умолчанию. Пока SMTP не настроен, проблема не проявляется (сервис просто логирует и ничего не ждёт) — но как только SMTP появится и почтовый провайдер хоть иногда подтормозит, это станет источником зависающих запросов. Задать явные короткие таймауты (секунды, не минуты по умолчанию) и не блокировать ответ клиенту ожиданием отправки письма — отправлять email фоново там, где он не критичен для результата операции (`void this.email.send(...)` без `await`, либо через очередь из P0.5, если до неё дойдёт). Тот же принцип — явный короткий таймаут, а не библиотечный дефолт — заложить заранее и для будущих внешних интеграций (SMS-шлюз, банк/ОФД из P0.1, P2.9), чтобы зависший сторонний сервис не замораживал потоки приложения.

**P3.24. `DEPLOY_GUIDE.md` сам рекомендует вход под root и допускает пароль вместо SSH-ключа — осознанный компромисс ради простоты для нетехнического читателя на первом деплое, но не то, с чем стоит оставаться перед реальными платежами.** Проверено дословно: гайд инструктирует подключаться командой `ssh root@ВАШ_IP_АДРЕС`, а в разделе выбора способа входа прямо пишет «Если умеете пользоваться SSH-ключами — выбирайте вход по ключу (безопаснее). Если нет — выбирайте вход по паролю» — то есть пароль как равноправная опция для тех, кто не умеет в ключи, а не аварийный fallback. Нигде в гайде нет упоминания смены порта SSH с 22 на нестандартный, `fail2ban`, лимита `nofile`/ulimit. Это не случайная недоработка — весь гайд написан для нетехнического владельца клуба, разворачивающего сервер впервые, и требование сразу настроить SSH-ключи реально может кого-то остановить ещё до установки Docker. Но раз система обрабатывает реальные платежи и медицинские данные, это стоит закрыть явно, а не оставлять на усмотрение конкретного читателя:
- Добавить в `DEPLOY_GUIDE.md` отдельный шаг «после того как всё заработало» (не блокирующий первый деплой, но обязательный перед реальными платежами): непривилегированный пользователь с `sudo` вместо работы под `root`, SSH-ключ вместо пароля, отключение входа по паролю и под `root` в `sshd_config`, смена порта SSH на нестандартный.
- Установить и включить `fail2ban` — блокировка по IP при переборе пароля/сканировании, отдельная страховка даже после перехода на ключи.
- Поднять `nofile` (ulimit) до 65535 — дефолтные 1024 в Ubuntu рассчитаны не под десятки одновременных соединений от кластера PM2 (P3.18) и пула Postgres разом; при реальной нагрузке лимит может исчерпаться раньше, чем ожидается, и это будет выглядеть как случайные обрывы соединений без явной причины в логах приложения.
- Порт Postgres (5432) уже сейчас НЕ проброшен наружу — ни в `docker-compose.prod.yml` (у сервиса `postgres` нет секции `ports:`), ни, соответственно, в правилах `ufw` из гайда. База физически недостижима из интернета без входа на сам сервер. Это уже сделано правильно — отмечаю явно, чтобы не дублировать работу, а не потому что это баг.
- **Синхронизация времени (NTP).** Не проверено кодом (это состояние конкретной машины, не репозитория) — но стоит явно подтвердить на реальном сервере, что `systemd-timesyncd`/`chrony` включён и часы не дрейфуют. Рассинхронизация времени на сервере срывает проверку срока действия JWT (P3.8) и TLS-сертификатов (P0.3), путает временные метки в `activity-log` и логах, и может незаметно сдвигать расписание cron-задач (бэкапы из P3.3, ротация из P3.16/P3.21). Большинство современных хостеров включают NTP по умолчанию на образе — но это стоит один раз проверить (`timedatectl status`), а не предполагать.

**P3.25. Базовая production-гигиена самого Docker-описания не закрыта.** Четыре отдельных, проверенных по коду находки, каждая — типовой пункт чек-листа перед реальным продом:
- **Оба контейнера (`api`, `web`) работают от `root` внутри себя.** Ни в `api/Dockerfile`, ни в `web/Dockerfile` нет директивы `USER` — по умолчанию процесс в контейнере выполняется от root. Это не даёт атакующему root на самом VPS (контейнер всё равно изолирован), но при компрометации приложения (RCE через уязвимую зависимость, например) увеличивает, что именно атакующий сможет сделать внутри контейнера. Добавить непривилегированного пользователя в оба образа (`node:22.11.0-slim` уже включает готового пользователя `node`) и переключаться на него перед `CMD`.
- **`nginx:alpine` не закреплён по версии**, в отличие от продуманного точного пина Node (`node:22.11.0-slim`, с объяснением в комментарии, почему именно так). Плавающий тег `alpine` означает, что пересборка образа в разное время может подтянуть разные патч-версии nginx без предупреждения — сборка не воспроизводима. Закрепить на конкретный тег (например, `nginx:1.27-alpine`), обновлять осознанно.
- **Ни у одного сервиса не заданы лимиты ресурсов.** Ни `mem_limit`/`cpus` (Compose v2), ни `deploy.resources.limits` — ни для `postgres`, ни для `api`, ни для `web`. Без явных лимитов один разросшийся процесс (например, утечка памяти из P3.17 или тяжёлый запрос) может забрать всю доступную RAM/CPU хоста и задушить остальные контейнеры, включая саму базу данных — вместо того чтобы упасть по OOM изолированно и предсказуемо. Задать разумные лимиты на каждый сервис под целевую конфигурацию (12 ГБ RAM/6 vCPU на троих — Postgres, API, web).
- **У `api` и `web` нет собственного `healthcheck`, только у `postgres`.** `web` стартует по `depends_on: - api` без условия готовности — Docker Compose знает только, что контейнер `api` запущен, а не что API реально отвечает на запросы (при медленном старте — миграции, `npx prisma generate` — какое-то время `web` будет проксировать в ещё не готовый бэкенд и отдавать 502). Добавить `healthcheck` на `GET /health` (появится по P3.7) для `api`, и завязать `web` на `condition: service_healthy` тем же способом, каким `api` уже завязан на `postgres`.

**P3.26. CORS открыт для всех источников без необходимости.** Проверено: `app.enableCors()` в `api/src/main.ts` вызван без единого параметра — в NestJS это означает `origin: true`, то есть API принимает и подтверждает кросс-origin запросы с ЛЮБОГО сайта, а не только со своего фронтенда. При этом в проде API и так работает исключительно через тот же origin, что и фронтенд — весь трафик идёт через `nginx.conf` (`location /api/ { proxy_pass http://api:3000/api/; }`, тот же порт 80/домен, что и статика) — то есть широкий CORS сейчас не нужен вообще ни для чего рабочего, а только расширяет поверхность атаки: если JWT-токен клиента когда-либо станет доступен стороннему JS (например, через XSS на совершенно другом сайте, если токен лежит в местах, откуда его можно достать скриптом), открытый CORS облегчает использование этого токена с чужого домена. Ограничить `origin` явным списком (домен фронтенда, плюс `http://localhost:5173`/аналог для локальной разработки через переменную окружения) вместо `true`, либо, раз API и фронтенд всегда на одном origin в проде, включать CORS только в dev-режиме и не включать его вовсе в `NODE_ENV=production`.

## Приоритет 4 — то, что отличает продукт для сети одного владельца от продукта на продажу другим клубам

(в 0.1.0 явно заявлена цель мультиарендности «на будущее»; Приоритет 1 выше закрывает сеть **одного** владельца — здесь речь про полностью чужих, не связанных между собой владельцев на одной системе)

**P4.1. Реальный тест изоляции между независимыми владельцами.** Не путать с сетью одного CEO из Приоритета 1: здесь нужен тестовый второй `Network`/CEO, никак не связанный с первым, чтобы подтвердить, что STAFF/CEO одной сети не может дотянуться до клиентов/финансов чужой сети через подбор ID.

**P4.2. Настраиваемые цены/тарифы и часы работы на уровне зала/сети**, а не только `MembershipPricing` — проверить, что расписание, зоны клининга (сейчас захардкожено «7 зон»?) и список тарифов действительно настраиваются под конкретного владельца, а не перенесены как константы из демо SiberianGym.

**P4.3. Экспорт отчётов для бухгалтерии.** Экспорт в PDF был осознанно отложен в 0.10.0. Для реальной бухгалтерии важнее не PDF, а выгрузка в Excel/CSV (в идеале — формат, который можно скормить 1С) по выручке, транзакциям и остаткам склада — без этого бухгалтер клуба не сможет свести месяц.

**P4.4. Промокоды/рефералки/корпоративные абонементы.** Стандартные инструменты продаж клуба, которых сейчас нет ни в модели данных, ни в API.

## Как работать с этим списком

Не пытайся закрыть всё одним PR. Начни с Приоритета 0 целиком (это блокеры для легального приёма денег, включая приём чеков и работу с несовершеннолетними). P0.2 (приём чека) — самый инвазивный пункт во всём Приоритете 0, потому что оборачивает все существующие денежные эндпоинты: имеет смысл делать его сразу после P0.1 (наличие хотя бы одной работающей сертифицированной кассы — организационный шаг, не код), пока эти денежные пути ещё немногочисленны, а не откладывать на потом, когда к ним добавится Приоритет 1. Самостоятельная онлайн-оплата картой (P2.9, бывший P0.2 в исходной версии этого документа) сознательно вынесена из блокеров запуска — P0.1+P0.2 достаточно, чтобы легально и без ручного «на глаз» принимать деньги через администратора уже в первый день. Приоритет 1 (сеть залов) — следующий по важности именно потому, что это изменение модели данных: если сначала сделать заморозку абонемента, контроль доступа и отчётность CEO в расчёте на один `gymId` (Приоритет 2), их придётся переделывать, когда появится сеть. Дальше — Приоритет 2 по пунктам в порядке важности для операционки клуба, и только потом Приоритет 3 и 4. По каждому пункту:
1. Опиши затрагиваемые модули (`api/src/...`, `web/src/features/...`) перед началом работы.
2. Добавь миграцию Prisma, если меняется модель данных.
3. **Перед добавлением нового enum'а, статуса, поля или массива-константы — проверь grep'ом, не существует ли уже в коде похожий список того же смысла** (enum в `prisma/schema.prisma`, массив констант на фронтенде, список типов транзакций/источников выручки и т.п.). Если расширяешь существующую сущность — обнови все места, которые её используют, а не только точку добавления; не создавай второй параллельный источник истины для одного и того же понятия.
4. Обнови `CHANGELOG.md` в существующем стиле проекта (Добавлено/Исправлено/Проверено), включая ручной или автоматический сценарий проверки — обязательно с меткой номера пункта, см. правило ниже.
5. Если пункт противоречит уже принятому в проекте решению (например, «оплата вручную» из 0.1.0), явно зафиксируй, что это решение пересматривается и почему.

## Обязательная фиксация в CHANGELOG и контроль выполнения

Работа по пункту из этого документа не считается выполненной, пока она не отражена в `CHANGELOG.md` — код без записи в чейнджлоге не в счёт, каким бы маленьким ни было изменение. Смысл всего этого раздела — чтобы в любой момент можно было однозначно сверить «что заявлено сделанным» с «что реально сделано», а не верить на слово последнему коммиту.

### Правило маркировки записей

Каждая запись в `CHANGELOG.md`, закрывающая (полностью или частично) пункт из этого документа, обязана начинаться с метки номера пункта в квадратных скобках:

```
### Добавлено
- **[P0.2]** Добавлена сущность `Order`/`OrderLine`, эндпоинты подтверждения заказа сканированием чека...
```

- Если одна доработка закрывает несколько пунктов сразу — перечислить все метки: `[P1.1][P1.7]`.
- Если пункт сделан **не полностью** — не ставить метку так, будто он закрыт целиком. Писать явно: `[P2.4, частично: только Web Push, SMS не подключён]`. Ложное «готово» опаснее отсутствия записи вообще, потому что его не отловит даже ручная сверка.
- Метка должна встречаться в CHANGELOG ровно один раз на «финальное» закрытие пункта — если пункт переоткрывается и дорабатывается позже, это новая запись в новой версии, а не правка задним числом старой.

### Инструменты проверки «что сделано, а что нет»

1. **Грep по CHANGELOG.** `grep -oE '\[P[0-4]\.[0-9]+' CHANGELOG.md | tr -d '[' | sort -u` — список всех меток, реально закрытых по чейнджлогу на текущий момент. Быстрая ручная сверка с таблицей статуса выше — не требует написания кода, годится как первая проверка при каждом ревью PR.

Подключить как шаг в CI (P3.2) — минимум предупреждением в выводе сборки, в идеале — падающей проверкой на несостыковке №1.
3. **Раздел «Проверено» как единственное основание перевести пункт в «сделано».** Статус пункта нельзя менять на «сделано» только потому, что код написан и слит в основную ветку — нужен пройденный сценарий в разделе «Проверено» соответствующей версии CHANGELOG (или автотест из P3.1, если он уже покрывает сценарий и указан там же) — то есть то же правило, что в проекте действует с версии 0.1.0, здесь оно явно привязывается к номеру пункта.
4. **Ручная сверка перед каждым релизом.** Раз в релиз (необязательно раз в спринт) CEO или ответственный за приёмку вручную проходит по пунктам со статусом «сделано» и сверяет заявленное поведение с реальным в проде — это не замена автотестам и скрипту выше, а отдельная проверка на случай, когда код и CHANGELOG формально совпадают, но фактическое поведение в проде отличается (например, из-за незадеплоенной миграции или невыполненного шага из README по продакшн-деплою).

## Приложение: черновики текстов согласий, разрешений и отказов

**Это не юридическая консультация.** Тексты ниже — рабочие черновики, собранные по обычной практике оформления таких форм в РФ (152-ФЗ «О персональных данных», 38-ФЗ «О рекламе», ГК РФ о дееспособности несовершеннолетних), чтобы Claude Code было с чего начать вёрстку экранов согласия и хранение текста версии согласия в БД. Перед вводом в эксплуатацию — особенно разделы про несовершеннолетних и данные о здоровье — тексты должен проверить и утвердить юрист клуба применительно к конкретной организационно-правовой форме (ИП/ООО), ИНН и фактическому перечню обрабатываемых данных. Цена ошибки в этой части выше, чем в остальном списке.

В коде каждому тексту должна соответствовать версия (например `consentVersion: "2026-09-14"`), чтобы при изменении формулировок было видно, по какой именно версии клиент давал согласие.
