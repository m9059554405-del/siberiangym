# Инструкция по запуску SiberianGym — от теста на своём ПК до реального хостинга

Эта инструкция написана максимально простым языком — предполагается, что
вы не программист, но умеете пользоваться компьютером и не боитесь
копировать команды в чёрное окошко (терминал). Каждая команда объясняется:
что она делает и почему нужна именно она.

Инструкция состоит из семи частей:

1. [Термины простыми словами](#1-термины-простыми-словами)
2. [Тестовый запуск на своём компьютере](#2-тестовый-запуск-на-своём-компьютере)
3. [Что выбрать при покупке хостинга](#3-что-выбрать-при-покупке-хостинга)
4. [Установка на реальном сервере](#4-установка-на-реальном-сервере)
5. [Домен и «замочек» (HTTPS) — когда будете готовы](#5-домен-и-замочек-https--когда-будете-готовы)
6. [Фото клиентов — объектное хранилище (S3)](#6-фото-клиентов--объектное-хранилище-s3)
7. [Повседневная эксплуатация](#7-повседневная-эксплуатация)

В конце — смета расходов и список решений, которые сознательно отложены
на потом.

## 1. Термины простыми словами

Прежде чем начать, пять слов, которые будут встречаться постоянно:

- **Docker** — программа, которая упаковывает наше приложение вместе со
  всем, что ему нужно для работы (базу данных, Node.js и т.д.) в готовые
  «коробки» (называются *контейнеры*). Вам не нужно ничего настраивать
  руками — Docker сам всё соберёт по нашим инструкциям (`Dockerfile`,
  `docker-compose.prod.yml`), которые уже лежат в проекте.
- **VPS / хостинг / сервер** — арендованный компьютер в интернете,
  который работает круглосуточно (в отличие от вашего домашнего ПК,
  который вы выключаете). Именно на нём в итоге будет жить приложение
  для реальных клиентов зала.
- **SSH** — способ подключиться к арендованному серверу через текстовые
  команды. Это как удалённый рабочий стол, только без картинок — вы
  печатаете команду, сервер её выполняет и показывает результат текстом.
- **Домен** — человекочитаемый адрес сайта (например, `siberiangym.ru`)
  вместо набора цифр (IP-адреса вроде `185.12.34.56`). Пока домена нет,
  приложение открывается прямо по IP-адресу сервера — это нормально для
  теста и даже для первого времени работы.
- **HTTPS / SSL-сертификат** — тот самый замочек рядом с адресом сайта в
  браузере, шифрует данные между клиентом и сервером. Настраивается один
  раз, после того как появится домен (см. часть 5).

Ещё один важный момент: **тестовый запуск на своём ПК** (часть 2) и
**реальный хостинг** (части 3–4) — это буквально одни и те же команды,
применённые в двух разных местах. Правильно один раз потренироваться у
себя на компьютере, набить руку — а потом повторить то же самое на
арендованном сервере уже для реальных клиентов.

## 2. Тестовый запуск на своём компьютере

Цель этой части — увидеть работающее приложение у себя на компьютере,
без хостинга и без интернета (кроме первого запуска, когда Docker
скачивает нужные компоненты). Это идеальный способ протестировать всё
перед тем, как платить за сервер, а также потренироваться перед
реальным развёртыванием.

**Важно:** то, что запущено на вашем ПК, видно только на вашем
компьютере (и, при желании, устройствам в той же Wi-Fi сети — см. шаг
2.8). Реальные клиенты зала зайти сюда не смогут — для них нужен
отдельный сервер в интернете (часть 3–4).

### 2.1. Установите Docker Desktop

1. Откройте страницу [docker.com/products/docker-desktop](https://www.docker.com/products/docker-desktop/)
   и скачайте версию для Windows.
2. Запустите установщик. Если он предложит включить **WSL2** — соглашайтесь,
   это стандартный и рекомендованный вариант.
3. После установки Windows может попросить перезагрузить компьютер —
   перезагрузите.
4. Откройте Docker Desktop из меню Пуск и дождитесь, пока в левом нижнем
   углу появится зелёная надпись «Docker Desktop is running» (или похожая).
   Первый запуск может занять минуту-другую.

### 2.2. Откройте проект

У вас уже есть скачанный проект в папке `E:\project_prod`. Откройте
PowerShell (через меню Пуск наберите «PowerShell») и перейдите в эту папку:

```powershell
cd E:\project_prod
```

*(Если бы проекта не было — его можно было бы скачать командой
`git clone https://github.com/m9059554405-del/siberiangym.git`, но у вас
он уже есть, этот шаг просто для справки на будущее, например при
переустановке Windows.)*

### 2.3. Создайте файл с настройками

Приложению нужен файл с секретными настройками (пароли, ключи) — он
специально не хранится в самом проекте (в GitHub), чтобы пароли
случайно не попали в открытый доступ. Есть готовый пример-заготовка —
скопируйте его:

```powershell
Copy-Item .env.prod.example .env.prod
```

Теперь откройте `.env.prod` любым текстовым редактором (подойдёт обычный
Блокнот — правой кнопкой по файлу → Открыть с помощью → Блокнот) и
впишите значения. Вот что означает каждая строка:

```
POSTGRES_PASSWORD=...   ← пароль для базы данных. Придумайте длинную
                            случайную строку (см. ниже, как сгенерировать).
JWT_SECRET=...           ← секретный ключ, которым приложение подписывает
                            "пропуска" пользователей после входа. Тоже
                            длинная случайная строка, ДРУГАЯ, чем пароль
                            выше.
SEED_CEO_EMAIL=...       ← email первого аккаунта директора (CEO), под
                            которым вы войдёте в первый раз.
SEED_CEO_PASSWORD=...    ← пароль для этого аккаунта. Смените его после
                            первого входа прямо в приложении.
SMTP_...                 ← настройки почты для email-уведомлений. Для
                            теста на своём ПК можно оставить пустыми —
                            письма будут просто печататься в лог вместо
                            отправки, ничего не сломается.
```

Чтобы сгенерировать случайную строку для `POSTGRES_PASSWORD` и
`JWT_SECRET`, выполните в PowerShell дважды (один раз для каждого
значения — они обязательно должны отличаться друг от друга):

```powershell
-join ((48..57)+(65..90)+(97..122) | Get-Random -Count 40 | ForEach-Object {[char]$_})
```

Команда напечатает случайный набор букв и цифр — скопируйте его в
соответствующую строку файла `.env.prod`. Для теста на своём компьютере
это не критично (никто извне всё равно не достучится), но лучше сразу
привыкнуть делать правильно — на реальном сервере это уже будет важно.

Сохраните и закройте файл.

### 2.4. Запустите приложение

Одна команда поднимает сразу три части системы — базу данных, backend
(сервер с логикой) и frontend (то, что видит пользователь в браузере):

```powershell
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Что происходит: Docker скачивает базовые компоненты (если их ещё нет),
собирает приложение и запускает всё в фоне (флаг `-d` — «detached», не
занимает окно терминала). **Первый запуск может занять 5–15 минут** в
зависимости от скорости интернета и компьютера — это нормально, идёт
загрузка и сборка. Повторные запуски намного быстрее (минута или меньше).

Проверить, что всё поднялось, можно командой:

```powershell
docker compose -f docker-compose.prod.yml ps
```

Должно быть три строки (`postgres`, `api`, `web`) со статусом `running`
или `healthy`.

### 2.5. Создайте зал и первого директора (только один раз)

После первого запуска нужно один раз создать сам «зал» в базе данных и
первый аккаунт CEO — командой:

```powershell
docker compose -f docker-compose.prod.yml exec api node dist/prisma-seed/seed.js
```

Эта же команда заодно наполняет справочник упражнений (сейчас в нём 93
упражнения, 71 — с настоящими фото техники выполнения). Повторный
запуск этой команды безопасен — она не создаёт дубликаты, а только
добавляет то, чего ещё нет.

### 2.6. Откройте приложение в браузере

Перейдите на [http://localhost/](http://localhost/) — должна открыться
страница входа SiberianGym.

Войдите с email и паролем, которые вы указали в `SEED_CEO_EMAIL` /
`SEED_CEO_PASSWORD`. Вы попадёте в кабинет директора (CEO) — оттуда
можно создавать тренеров, администраторов и клиентов, смотреть на всё
как в реальном приложении.

### 2.7. Как остановить и снова запустить

Когда закончили тестировать, приложение можно остановить (данные при
этом сохраняются):

```powershell
docker compose -f docker-compose.prod.yml stop
```

Чтобы запустить снова в другой раз:

```powershell
docker compose -f docker-compose.prod.yml start
```

### 2.8. Проверить с телефона (по желанию)

Если хотите посмотреть, как приложение выглядит на телефоне, находясь в
той же Wi-Fi сети:

1. В PowerShell выполните `ipconfig`, найдите строку `IPv4 Address` (что-то
   вроде `192.168.1.25`).
2. На телефоне, подключённом к той же Wi-Fi сети, откройте
   `http://192.168.1.25/` (со своим адресом).
3. При первом обращении Windows может спросить разрешение на доступ
   через брандмауэр — разрешите для «частных сетей».

### 2.9. Если что-то пошло не так

- **«Docker Desktop is not running»** — просто откройте приложение
  Docker Desktop и подождите, пока оно полностью загрузится, затем
  повторите команду.
- **Порт 80 занят** (редко, обычно если на компьютере уже работает
  Skype старой версии, IIS или другой веб-сервер) — увидите ошибку про
  порт при запуске. Проверить, что его занимает:
  ```powershell
  netstat -ano | findstr :80
  ```
  Либо остановите конфликтующую программу, либо это стоит просто
  учитывать — на реальном сервере (часть 3–4) порт 80 обычно свободен.
- **Посмотреть, что происходит внутри** (логи всех трёх частей):
  ```powershell
  docker compose -f docker-compose.prod.yml logs -f
  ```
  (`Ctrl+C`, чтобы выйти из просмотра логов — сами контейнеры при этом
  продолжают работать).
- **Начать полностью с чистого листа** (удаляет и базу данных — только
  если специально хотите стереть все тестовые данные):
  ```powershell
  docker compose -f docker-compose.prod.yml down -v
  ```
  После этого повторите шаги 2.4 и 2.5.

## 3. Что выбрать при покупке хостинга

Когда протестировали на своём ПК и всё понравилось — пора арендовать
настоящий сервер в интернете, доступный клиентам круглосуточно.

Рекомендация по провайдеру (подробное обоснование — в README.md
проекта): в первую очередь **Timeweb Cloud** — обычно лучшее соотношение
цена/надёжность для такой нагрузки (~330 пользователей, некрупный зал),
есть готовые образы с уже установленным Docker, младшие тарифы
недорогие. Как альтернатива, если важнее гарантии/SLA, чем цена —
**Selectel**. Есть и другие бюджетные варианты (Beget, RUVDS) — можно
свериться по актуальным ценам перед покупкой, но дальше в инструкции
ориентируемся на Timeweb Cloud, поскольку у него, как правило, самый
понятный интерфейс на русском языке.

**Важно:** цены и точный список опций у хостеров периодически меняются.
Ниже — что именно выбирать по смыслу (какие параметры важны и почему),
а не привязка к конкретным цифрам цен на момент чтения.

### Пошагово, что выбрать при создании сервера

1. Зарегистрируйтесь на сайте хостера (email/телефон, как в любом
   интернет-сервисе).
2. Найдите раздел вроде **«Облачные серверы»** и нажмите **«Создать
   сервер»**.
3. Дальше выбираете параметры — вот что важно на каждом шаге:

   **Локация / дата-центр**
   → Выбирайте российский дата-центр (например, Москва). Это важно по
   двум причинам: во-первых, юрисдикция хранения персональных данных
   клиентов (важно для соответствия закону о персональных данных),
   во-вторых — быстрее отклик для тренеров и клиентов, которые в России.

   **Образ системы (операционная система)**
   → Если у хостера есть готовый образ **«Docker»** в маркет-плейсе
   (у Timeweb Cloud такой обычно есть) — выбирайте его, это экономит
   один шаг установки. Если такого образа нет — выбирайте
   **Ubuntu 22.04 LTS (64-bit)**, Docker установим сами (см. часть 4,
   шаг 4.2).

   **Конфигурация (мощность сервера)**
   → Минимум: **2 vCPU, 4 ГБ RAM, 40–60 ГБ SSD**. Почему именно столько:
   на сервере одновременно работают база данных, backend-сервис и сборка
   frontend-приложения — при меньшем объёме памяти (например, 1–2 ГБ)
   первая же сборка образов может не пройти из-за нехватки памяти, а
   при живой нагрузке (несколько тренеров одновременно смотрят
   расписание) сервер может начать тормозить. Для одного зала на ~330
   пользователей этого с запасом хватит.

   **Сеть**
   → Убедитесь, что включён публичный **IPv4-адрес** (обычно это
   значение по умолчанию, но проверьте галочку) — без него до сервера
   не достучаться из интернета.

   **Резервное копирование (бэкапы)**
   → Если хостер предлагает автоматические снапшоты/бэкапы за
   небольшую доплату — рекомендую включить. Это отдельная страховка
   на случай сбоя сервера, вдобавок к бэкапам самой базы данных (часть 6).

   **Способ входа (аутентификация)**
   → Если умеете пользоваться SSH-ключами — выбирайте вход по ключу
   (безопаснее). Если нет — выбирайте вход по паролю, но задайте
   **длинный и сложный** пароль и сохраните его в надёжном месте
   (например, в менеджере паролей) — этот пароль будет пропуском ко
   всему серверу.

   **Оплата**
   → Для начала выбирайте помесячную оплату — так проще поменять
   тариф или переехать к другому хостеру, если что-то не устроит.
   Годовую оплату со скидкой имеет смысл рассматривать позже, когда
   всё уже проверено и стабильно работает.

4. После создания сервера хостер покажет его **IP-адрес** — обязательно
   сохраните его, он понадобится на каждом следующем шаге.

## 4. Установка на реальном сервере

Все команды ниже выполняются **на сервере**, через SSH-подключение —
это то самое «чёрное окошко», которое подключается к арендованному
компьютеру, а не к вашему.

### 4.1. Подключитесь к серверу по SSH

В Windows 10/11 SSH уже встроен, отдельная программа не нужна. Откройте
PowerShell и наберите:

```powershell
ssh root@ВАШ_IP_АДРЕС
```

(замените `ВАШ_IP_АДРЕС` на адрес, который дал хостер). При первом
подключении появится вопрос про «fingerprint» — наберите `yes` и
нажмите Enter. Дальше введите пароль от сервера (тот, что задавали при
создании, или что прислал хостер на почту) — при вводе пароля символы
не отображаются, это нормально, просто печатайте и нажимайте Enter.

Если всё получилось — приглашение в терминале изменится на что-то вроде
`root@имя-сервера:~#` — вы «внутри» сервера.

### 4.2. Установите Docker (если ещё не установлен)

Если при заказе сервера вы выбрали готовый образ с Docker — этот шаг
можно пропустить (проверьте командой `docker --version` — если версия
показалась, всё уже стоит).

Если Docker ещё нет — официальный скрипт установки (выполняется на
самом сервере, в SSH-сессии):

```bash
curl -fsSL https://get.docker.com | sh
```

Дождитесь окончания (пара минут), затем проверьте:

```bash
docker --version
docker compose version
```

Обе команды должны показать номер версии, а не ошибку.

### 4.3. Скачайте проект

```bash
git clone https://github.com/m9059554405-del/siberiangym.git
cd siberiangym
```

### 4.4. Создайте файл с настройками — уже РЕАЛЬНЫЕ значения

Это самый важный шаг — здесь задаются настоящие пароли, которые будут
защищать реальные данные клиентов зала. **Не используйте те же
значения, что были в тестовом `.env.prod` на своём ПК** — сделайте
новые.

```bash
cp .env.prod.example .env.prod
nano .env.prod
```

`nano` — простой текстовый редактор прямо в терминале. Стрелками
перемещаетесь по тексту, печатаете как обычно. Когда закончите:
`Ctrl+O` → Enter (сохранить), затем `Ctrl+X` (выйти).

Чтобы сгенерировать случайную строку прямо на сервере (для
`POSTGRES_PASSWORD` и отдельно для `JWT_SECRET` — обязательно два
разных значения):

```bash
openssl rand -base64 48
```

Выполните эту команду дважды, каждый раз копируя результат в
соответствующую строку файла.

`SEED_CEO_EMAIL` и `SEED_CEO_PASSWORD` — задайте настоящий email и
пароль, под которым вы (или назначенный директор) будете реально
входить в систему. `SMTP_*` пока можно оставить пустыми — это
соответствует решению проекта запускаться с email-уведомлениями,
но настроить SMTP можно и чуть позже, ничего не сломается — письма
пока просто будут только логироваться, а не отправляться.

### 4.5. Откройте нужные порты (firewall)

Ubuntu поставляется с `ufw` (простой firewall). Настройте так, чтобы не
закрыть себе же доступ по SSH:

```bash
ufw allow 22
ufw allow 80
ufw allow 443
ufw enable
```

(порт 22 — SSH, которым вы сейчас подключены; 80 — обычный веб-доступ;
443 — понадобится позже для HTTPS, часть 5). На вопрос про подтверждение
ответьте `y`.

Первый запуск — несколько минут (сборка образов). Проверить статус:

```bash

```

### 4.7. Создайте зал и первого директора

Тоже один раз, как в части 2:


### 4.8. Откройте приложение

В браузере на любом устройстве (уже не обязательно на самом сервере):

```

```

Войдите с `SEED_CEO_EMAIL` / `SEED_CEO_PASSWORD`. Дальше директор из

## 5. Домен и «замочек» (HTTPS) — когда будете готовы

Пока домена нет — приложение прекрасно работает и по IP-адресу, как в
части 4: программа (Caddy) уже встроена в `docker-compose.prod.yml` и
сама решает, работать ли по HTTP на порту 80 или переключиться на
HTTPS — в зависимости от одной строчки в `.env.prod`. Домен и HTTPS
можно подключить в любой момент позже, без переустановки всего
остального и без единой ручной команды на сервере, кроме передеплоя.

**Через обычный HTTP (без замочка) из браузера в сторону сервера уходят
пароли при входе и личные данные клиентов зала в открытом виде** — это
нормально для теста на своём ПК (часть 2), но для реального сервера с
настоящими клиентами домен и HTTPS стоит подключить как можно раньше
после первого запуска, а не откладывать надолго.

Когда домен появится:

1. **Купите домен** у любого регистратора (например, reg.ru, или прямо
   у хостера — у Timeweb Cloud тоже есть регистрация доменов).
2. **Настройте A-запись** домена на IP-адрес сервера — в панели
   управления доменом (у регистратора) находите раздел «DNS-записи» или
   «Управление зоной» и добавляете запись типа `A`, значение — IP-адрес
   вашего сервера. Изменения обычно применяются от нескольких минут до
   пары часов — **дождитесь, пока домен реально откроет ваш сервер по
   обычному HTTP** (`http://ваш-домен.ru/`), прежде чем переходить к
   следующему шагу: если A-запись ещё не применилась, Let's Encrypt не
   сможет подтвердить, что домен ваш, и сертификат не выдастся.
3. **Впишите домен в `.env.prod`** на сервере (`nano .env.prod`, как в
   части 4.4) — найдите строку `DOMAIN=` и допишите ваш домен без
   `http://` и без `www.`, например:

   ```
   DOMAIN=siberiangym.ru
   ```

   Сохраните (`Ctrl+O` → Enter) и закройте (`Ctrl+X`).
4. **Передеплойте** той же командой, что уже использовали:

   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
   ```

   Caddy сам получит сертификат Let's Encrypt в течение примерно
   минуты и с этого момента сайт будет открываться на
   `https://ваш-домен.ru` с замочком в браузере, а обращения по
   обычному `http://` автоматически перенаправятся на `https://`.

Проверить, что сертификат получен, можно логами: `docker compose -f
docker-compose.prod.yml logs caddy` — там будет видно `certificate
obtained successfully`. Если вместо этого видно ошибки про DNS/таймаут —
скорее всего A-запись ещё не применилась или порт 80/443 закрыт
firewall'ом (часть 4.5) — подождите и попробуйте передеплой ещё раз.

## 6. Фото клиентов — объектное хранилище (S3)

Приложение принимает от клиентов фото прогресса, фото еды и фото
профиля. Без объектного хранилища эти фото либо не загрузятся вовсе на
реальном телефоне (фото с камеры «в хорошем качестве» — обычно
несколько мегабайт, а без этого шага система ограничена гораздо
меньшим объёмом), либо будут храниться прямо в базе данных, раздувая
её и замедляя всё остальное. Настройка ниже — рекомендуется сделать до
того, как клиенты начнут активно пользоваться разделом «Прогресс», но
без неё остальная часть приложения (оплаты, расписание, склад и т.д.)
продолжает работать нормально — просто кнопки загрузки фото будут
показывать ошибку.

### 6.1. Закажите S3-хранилище у провайдера

Рекомендация (подробнее — в README.md): **Selectel S3** — российский
провайдер объектного хранилища, целевая конфигурация проекта
рассчитана на отдельное S3-хранилище именно у такого провайдера (а не
на использование места на самом сервере приложения). В панели
управления провайдера:

1. Создайте S3-хранилище (бакет), например с именем `siberiangym-media`.
2. Включите **публичный доступ на чтение** для объектов в этом бакете —
   без этого браузеры клиентов не смогут открыть загруженные фото по
   прямой ссылке (панель провайдера обычно называет это «публичный
   контейнер» или «public-read»).
3. Создайте ключ доступа (access key + secret key) с правами на запись
   в этот бакет — панель провайдера покажет их один раз, сохраните
   сразу в надёжном месте.
4. Запишите себе: **endpoint** (адрес API хранилища), **регион**,
   **имя бакета**, **access key**, **secret key** и **публичный домен**
   бакета (по которому будут открываться сами фото — провайдер обычно
   показывает его отдельно от endpoint).

### 6.2. Впишите данные в `.env.prod`

На сервере, тем же способом, что в части 4.4 (`nano .env.prod`),
заполните блок с `S3_`-переменными значениями от провайдера:

```
S3_ENDPOINT=https://s3.ru-1.storage.selcloud.ru      ← endpoint провайдера
S3_REGION=ru-1                                         ← регион
S3_BUCKET=siberiangym-media                            ← имя бакета
S3_ACCESS_KEY_ID=...                                   ← из шага 6.1.3
S3_SECRET_ACCESS_KEY=...                               ← из шага 6.1.3
S3_PUBLIC_URL=https://siberiangym-media.s3.ru-1.storage.selcloud.ru  ← публичный домен бакета
```

`S3_FORCE_PATH_STYLE` для реального провайдера оставьте `false` (это
нужно только для MinIO при локальной разработке).

### 6.3. Передеплойте

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Приложение само создаст бакет, если он ещё не существует (для
большинства провайдеров ключ доступа должен иметь права на это; если
бакет уже создан вручную на шаге 6.1 — этот шаг просто ничего не
сделает). Проверить, что всё настроено правильно, можно, загрузив
тестовое фото прогресса в приложении под любым клиентским аккаунтом —
если фото отобразилось сразу после загрузки, всё работает.

## 7. Повседневная эксплуатация

### Обновление после изменений в коде

Когда в проект вносятся изменения (новая версия), на сервере:

```bash
cd siberiangym
git pull
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Миграции базы данных применяются автоматически при каждом запуске —
это безопасно, уже применённые миграции просто пропускаются.

### Резервное копирование (бэкапы)

Два независимых уровня защиты — рекомендую оба:

1. **Автоматические снапшоты хостера** — если включили при заказе
   сервера (часть 3), они уже работают в фоне, ничего дополнительно
   делать не нужно.
2. **Автоматическая резервная копия PostgreSQL в S3** — скрипт
   `scripts/backup-postgres.sh` делает сжатый custom-format `pg_dump`,
   загружает файл в S3-префикс `backups/postgres/`, задаёт lifecycle с
   хранением `BACKUP_RETENTION_DAYS` дней и удаляет старые локальные файлы.
   Ключи S3 берутся из `.env.prod`; при их отсутствии скрипт всё равно
   создаёт локальную копию и явно пишет предупреждение.

   Разрешите запуск скрипта и добавьте ежедневный cron от root (путь
   замените на фактический каталог проекта):

   ```bash
   chmod 700 scripts/backup-postgres.sh scripts/restore-postgres.sh
   (crontab -l 2>/dev/null; echo "15 3 * * * /opt/siberiangym/scripts/backup-postgres.sh >> /var/log/siberiangym-backup.log 2>&1") | crontab -
   ```

   Ручной запуск для проверки:

   ```bash
   scripts/backup-postgres.sh
   ```

   Скрипт восстановления намеренно требует отдельного подтверждения
   `RESTORE` и должен запускаться только против disposable-копии окружения,
   а не боевой базы:

   ```bash
   scripts/restore-postgres.sh /var/backups/siberiangym/siberiangym-2026-09-18T03-15-00Z.dump
   ```

   После восстановления проверьте число миграций и несколько критичных
   таблиц (`users`, `clients`, `orders`, `transactions`). Тест полного
   восстановления следует выполнять на отдельном сервере/временном VPS
   минимум раз в квартал; результат фиксируйте в журнале эксплуатации.

   Для S3-копии можно указать `s3://bucket/key` вместо локального файла:

   ```bash
   scripts/restore-postgres.sh s3://siberiangym-media/backups/postgres/<file>.dump
   ```

### Логи и диагностика

Посмотреть, что происходит внутри приложения (полезно, если что-то не
работает):

```bash
docker compose -f docker-compose.prod.yml logs -f --tail=100
```

### Перезапуск

Если что-то зависло и нужно просто перезапустить всё:

```bash
docker compose -f docker-compose.prod.yml restart
```

### Если сайт не открывается

1. Проверьте, что все три части запущены:
   `docker compose -f docker-compose.prod.yml ps` — все три строки
   должны быть `running`/`healthy`.
2. Посмотрите логи (команда выше) — там обычно видна причина.
3. Проверьте, что firewall не заблокировал порт 80 (часть 4.5).

## Смета расходов (ориентировочно)

Точные цены нужно свериться на момент покупки — но по порядку величины:

- **VPS** (2 vCPU / 4 ГБ RAM, рекомендованная конфигурация) — обычно
  несколько сотен — ~1000 рублей в месяц у бюджетных российских
  провайдеров.
- **Домен** — от ~200 до ~800 рублей в год, зависит от зоны (`.ru`
  обычно дешевле).
- **SMTP для email-уведомлений** — можно начать бесплатно (Yandex,
  Mail.ru предлагают бесплатную отправку почты со своего домена при
  небольших объёмах), платный SMTP-сервис не обязателен на старте.
- **Приём платежей (Альфа-Банк или другой провайдер)** — отдельная
  история, не связана с хостингом; комиссии и тарифы обсуждаются
  отдельно, когда дойдёт очередь до самостоятельной оплаты клиентами
  (см. напоминание ниже).
